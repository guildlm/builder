THE SIGNAL IS FREE AND NOBODY READS IT

    If round N and round N+1 report the SAME failure text, the loop has stalled and the
    remaining rounds will not recover it. Two for two here, and both shipped NOT-GREEN.

Wasted model rounds in this corpus: taskapi 3, expreval 4 — SEVEN rounds of best-of-N fix
calls that could not have helped, on a corpus of twenty specs. taskapi alone made 30 model
fix calls. The budget is spent to its last round every time because nothing compares this
round's failure to the last one.

An early abort on a repeated failure is a small change and it is the RIGHT small change:
it would not fix anything, but it would stop pretending to. A NOT-GREEN tree that stops at
round 2 is the same artifact as one that stops at round 5, minus four rounds of calls, and
it reports the stall honestly instead of burying it in a budget exhaustion.

THIS BOUNDS THE PREVIOUS FINDING, AND I SAY SO PLAINLY
FINDING-the-model-fix-reintroduces-what-the-gate-just-repaired.txt documents a
repair-regress cycle on taskapipro and asks whether it generalises. It does NOT. Neither
stalled spec shows it; both show a single unfixed failure repeating. The repair-regress
cycle is one observation on one spec, and against the corpus it is the LESS common pattern
and the more benign one — taskapipro is progressing, which taskapi and expreval never did.

    I framed taskapipro's slow rounds as the pathology. The corpus says the pathology is
    the specs that never move at all, and taskapipro is the healthy case.

WHAT THE STALLS WERE ACTUALLY ABOUT — and it is already recorded
taskapi's four repeated rounds are the nil-slice defect the empty-list closure caught. That
is the closure working exactly as designed: the test named the invariant, the invariant was
violated, and the suite refused to go green. The loop then could not repair it, which is
the separate known problem recorded at da248de ("the fix loop widens inside the failing
test's package, and the defect is one layer down"). So taskapi's NOT-GREEN is a SUCCESS of
the defence and a FAILURE of the repair, and those two facts have been reported as one
number all week.

expreval's is a genuine implementation defect — a parser returning 1 for "1+2" — with no
closure involved.

CORRECTION AND QUANTIFICATION (~10:32) — THE BUILDER ALREADY HAS THIS DETECTOR
==============================================================================
The title of this file is wrong and the sentence "nothing compares this round's failure to
the last one" is false. Found by reading the tail of a stalled log instead of its rounds:

    [guildlm-build] error surface repeats — stopping extension rounds
    [guildlm-build] exhausted 6 fix rounds (5 budgeted), still failing

The mechanism is in src/builder.py:

    seen_surfaces: set[str] = set()
    sig = _error_signature(output)
    if rnd > max_fix_rounds and sig in seen_surfaces:
        _log("error surface repeats — stopping extension rounds")

So the comparison exists, the signature function exists, and the abort exists. What is
scoped is WHEN it may fire: `rnd > max_fix_rounds` means the check runs ONLY on rounds
granted BEYOND the flat budget. Inside the budget a repeated surface is not checked at all.

IT IS A PERFECT PREDICTOR IN BOTH REGIMES — 125 detections, 0 recoveries

    builder's own detector (extension rounds)   100 logs   0 converged to green
    an in-budget repeat (this tool's signal)     25 logs   0 converged to green

Every one of the 125 ended "still failing". And when the builder's detector does fire it
stops immediately: 0 fix rounds and 0 model fix calls appear after that line, in any log. So
the builder is not ignoring the signal — it is refusing to look at it early.

THE COST OF LOOKING LATE, MEASURED
Across the 20 logs where both detectors fired, the in-budget signal precedes the builder's
by a mean of 2.1 rounds and 43 rounds in total. Those are rounds run inside the budget after
the error surface had already repeated once — each one a full compile/test cycle plus
best-of-N model fix calls, and none of the 125 runs recovered from that state.

THE CHANGE IS THEREFORE NOT "BUILD AN ABORT". It is deleting four words:

    if rnd > max_fix_rounds and sig in seen_surfaces:      ->      if sig in seen_surfaces:

with the evidence being 125 for 125. That is a much smaller and much better-supported change
than the one this file originally proposed, and I would not have found it by reasoning about
the design — only by reading the last four lines of a log I had already parsed twice for
something else.

WHAT I GOT WRONG AND WHY IT IS THE SAME MISTAKE AS THE REST OF TODAY
I parsed these logs for round headers and error lines, concluded "nothing reads the signal",
and never read the END of the file. The parser answered its query correctly; the query was
about rounds and the answer I wanted was about the run. Same shape as the nine invented
timestamps, the ledger omission, and the generation-keyed diff: right answer, wrong subject.

⚠️ ONE-LINE CHANGES TO src/ ARE STILL src/ CHANGES. This waits for the draws to drain like

both detectors fired and is the honest number for what the change would have saved.
