FINDING — the cross-package API block silently drops every sentinel declared in a var block
=============================================================================================
31 July, found by chasing why the first cross-process control failed where three earlier controls
went green. Logs and archived snapshots only, no GPU. builder.py is FROZEN under the running parity
experiment, so this is measured and queued, not applied.

HOW IT WAS FOUND — the green-to-red flip had a cause after all
    ledger-xproc-ctl-1 exhausted 6 rounds on ONE error, unchanged from round 2 to round 6:

        internal/api/response.go:30:29: undefined: models.ErrInsufficientFunds

    The as-drawn diff between that draw and the green one is a SINGLE IDENTIFIER:

        parity ctl-1   ErrInsufficientFunds = errors.New("insufficient funds")
        xproc  ctl-1   ErrInsufficient      = errors.New("insufficient funds")

    Same string, different name. response.go — a DIFFERENT package, generated later — wrote
    `models.ErrInsufficientFunds` in both draws. In the first it happened to guess the name models.go
    had chosen. In the second it did not, and the project never compiled.

    ⚠️ AND THE STRIPPER WAS RULED OUT BY ITEM 3, SHIPPED THIS AFTERNOON. Zero "stripped redeclared
    symbols" lines in the whole log, so FIX 2's widened decl set did not remove it — the model simply
    chose a different name. That is a generation difference across processes, NOT a regression from
    any of today's seven builder.py commits. The logging paid for itself within four hours.

THE MECHANISM — response.go was never told the name
    Rendering response.go's own context with internal/models/ already written:

        OTHER-PACKAGE APIs — import these; only exported names are visible:
        --- package models  (import "guildlm.dev/ledger/internal/models") ---
        type Account struct {...}
        func (a Account) Validate() error
        type Posting struct {...}
        type Transaction struct {...}

        contains "ErrInsufficient"        False
        contains "ErrInsufficientFunds"   False

    NO SENTINEL APPEARS AT ALL. A consumer that needs one is guessing.

THE BUG IS ONE REGEX, AND THE CODE BELIEVES IT DOES THE OPPOSITE
    exported_api() has a branch for var/const whose comment reads:

        else:  # var / const — keep exported singles (e.g. sentinel errors)
            vm = re.match(r"(?:var|const)\s+(\w+)", s)

    That matches `var ErrSolo = ...` and nothing else. A GROUPED declaration —

        var (
            ErrInvalid      = errors.New("invalid")
            ErrInsufficient = errors.New("insufficient funds")
        )

    — presents the line `var (`, where `\w+` cannot match `(`. The block's members are then visited
    individually, and none of them begins with var/const/func/type, so every one is skipped.

    MEASURED, both forms:
        single-line   var ErrSolo = ...        ->  'package models', 'var ErrSolo'      exposed
        grouped       var ( ErrA…; ErrB… )     ->  'package models'                     NOTHING

    The grouped form is idiomatic Go and is what every ledger and taskapi spec produces. So the
    branch written specifically to carry sentinel errors across a package boundary carries none of
    the ones this project actually declares.

HOW BIG — quantified across the archive
        completed builds                                       854
        ...whose log shows "undefined: pkg.Something"           99   (12%)
        ...specifically a cross-package SENTINEL (pkg.ErrX)     53   (6%)

        most-missed:  models.ErrInsufficientFunds 68 · service.ErrNotFound 66 · service.ErrExists 47

    Six percent of every build this campaign has run failed with an undefined cross-package sentinel,
    and the API block that exists to prevent exactly that has never carried one from a var block.

THE FIX, PROTOTYPED OUTSIDE THE FROZEN FILE AND VALIDATED
    Parse grouped var/const blocks and emit their exported members. On the real models.go:

        current    sentinels exposed: NONE
        prototype  sentinels exposed: ErrInvalid, ErrNotFound, ErrExists, ErrUnbalanced,
                                      ErrInsufficient

        single-line case unchanged, no duplicates        ['package models', 'var ErrSolo']
        const block, unexported member dropped           ['package x', 'const MaxN']

        archived as-drawn .go files whose API block would GAIN symbols:  46 of 475

    ⚠️ 46 OF 475 IS THE FILES THAT WOULD EXPORT MORE, NOT THE BUILDS THAT WOULD BE FIXED. A file only
    matters here if some OTHER package references one of its sentinels, and this does not measure
    that. It is an upper bound on reach, not a claim about repair.

⚠️ NOT APPLIED, AND WHY
    src/builder.py is hashed and locked by the freeze guard for the cross-process parity run in
    flight. An edit now would put some draws on one harness and the rest on another — the exact
    hazard the guard was built for this morning, and this finding is not urgent enough to justify
    breaking the experiment it came out of.

    ⚠️ AND IT IS A PROMPT CHANGE, so it alters what the model READS. Like the timestamp fix's third
    consumer, it must be verified by a BUILD and not only by a self-test, and its first check should
    be whether the sentinel actually gets used rather than merely offered.

⚠️ THE 69% AND THE 6% ARE DIFFERENT MEASUREMENTS AND MUST NOT BE QUOTED AS A TREND. 69% is of trees

generation, the fix loop repairs about three fifths of it, and the rest is fatal.

THE SHAPE IS STABLE, and that is the argument for fixing rather than tolerating it
    Five of the eight inspected individually. Every single one:

        internal/api/response.go  wants  models.ErrInsufficientFunds
        models' grouped block     offers ErrInsufficient, ErrExists, ErrInvalid, ErrNotFound,
                                         ErrUnbalanced

    response.go's chosen name is STABLE across draws and processes. models.go's is NOT — parity
    ctl-1 wrote the long name, xproc ctl-1 wrote the short one. So one file derives its name from
    the spec's prose ("insufficient funds") while the other abbreviates, and nothing in the prompt
    reconciles them. It is not drift; it is two files guessing independently because the channel
    that would tell them was empty.

THE FULL BLIND-SPOT LIST, and why the fix stays narrow
════════════════════════════════════════════════════════════════════════════════════════════
Before editing exported_api(), every Go declaration shape was fed through it. Three MORE blind
spots exist:

        shape                   exported today?   what the consumer sees
        single var                    YES         var ErrX
        GROUPED var                ** NO **       (nothing)
        single const                  YES         const MaxN
        GROUPED const              ** NO **       (nothing)
        type struct                   YES         full type
        GROUPED type               ** NO **       (nothing)
        type alias                    YES         type Alias = OtherThing
        func one-line                 YES         func F(a int) error
        func MULTI-LINE            TRUNCATED      func F(          <- no params, no return type
        method                        YES         func (t T) M() error
        interface with methods        YES         full interface

    A multi-line signature exported as `func F(` tells a consumer the function's name and nothing
    about how to call it. That looked like the more dangerous defect of the two.

THEN I COUNTED, AND THREE OF THE FOUR DO NOT OCCUR
        as-drawn non-test .go files: 475 across 50 trees

        shape                   files   trees
        grouped var                46      40      <- 80% OF TREES
        grouped const               0       0
        grouped type                0       0
        multi-line func sig         0       0

    So the fix stays exactly as prototyped: parse grouped var/const (const is the same code path
    and free), and leave grouped type and multi-line signatures alone.

    ⚠️ THE INSTINCT WAS TO FIX ALL FOUR. That would have added three untested code paths for shapes
    this corpus has never produced, in a function whose ONE existing branch for this was wrong for a
    month. Speculative generality in a parser is how the original bug survived: the var/const branch
    was written, believed, and never exercised against the form the generator actually emits.

    ⚠️ AND ZERO HERE MEANS ZERO IN THIS CORPUS — Go written by this model from these specs. A
    different spec style or model could emit grouped types tomorrow, and the shapes are recorded
    above so the next reader does not have to rediscover them. Known and unexercised is a different
    state from absent.

AND THE FOOTPRINT IS BIGGER THAN THE EARLIER NUMBER SUGGESTED: 40 of 50 trees contain a grouped var
block, not the 46-of-475 files quoted before. The file count understates it because one models.go
per tree carries every sentinel the whole project shares.

⚠️ FRAMING CORRECTED — see logs/FINDING-the-required-decls-gate-sees-a-third-of-what-the-purposes-
promise.txt. "Two files guessing independently because the channel was empty" is wrong. ledger's
spec NAMES the sentinels in models.go's own purpose ("ErrInvalid, ErrNotFound, ErrExists,
ErrUnbalanced, ErrInsufficientFunds"), and response.go — which receives every file's purpose — used
the long name CORRECTLY. models.go was told and did not comply. The API-block fix still stands (a
consumer should see what was actually declared) but the primary defect is upstream, in a file that
ignored its own purpose while _required_decls extracted nothing to enforce it.
