FINDING — the instruction carried; the REASON did not, and not even three lines
===============================================================================
2026-07-28. Controlled within one spec, one draw, one model: taskapipro-chain4.

THE COMPARISON, which was sitting in the spec the whole time

Two twin tests, identical in intent, in two different file entries.

  router_test.go entry (TASKS) — instruction PLUS ten lines of reason:

      "TestListDefaultsToTheConfiguredPageSize: ... newRouterWithPaging(2, 100),
       POST THREE tasks ... assert ... EXACTLY 2 come back.
       THE SMALL NUMBERS ARE THE POINT — do not 'simplify' them to the real defaults.
       The obvious version of this test is 'the default is 20, so POST 25 and expect
       20', and it is the version that CANNOT FAIL: with fewer than 21 items ... The
       witness has to sit ON the boundary, not past it — the same reason a bitset
       assertion at index 200 could not see a guard that moves at 128 ..."

  projects_test.go entry (PROJECTS) — the same instruction, no reason:

      "TestProjectListDefaultsToTheConfiguredPageSize: ... newRouterWithPaging(2, 100)
       ... POST THREE projects ... assert ... EXACTLY 2 come back."

RESULT, same draw:

    tasks     POSTed THREE, asserted 2   -> both paging mutations CAUGHT
    projects  POSTed ONE,   asserted 1   -> all three paging mutations SURVIVED

The projects test has the right name, calls the right helper with the right small values,
and asserts a plausible number. With one project in the store, a page size of 2 and a page
size of 7777 both return that one project. It cannot fail.

WHAT THIS ISOLATES

Everything else is held constant — same spec file, same generation, same model, same
sentence structure, the same literal instruction "POST THREE ... assert EXACTLY 2". The only
difference is whether the REASON was attached in that entry.

    The instruction alone was not enough. The instruction plus the reason was.

That is not what I would have guessed from the rest of tonight. The healthz failure taught
the opposite-looking lesson — an entry that explained a trap and then permitted the check
produced the wrong assertion twice, and WITHDRAWING the option is what fixed it. Both are
true and they are not in conflict:

    For an option you do not want exercised    -> withdraw it. Explaining is not a constraint.
    For a quantity that must be exact          -> give the reason. The number alone does not
                                                  survive contact with a plausible alternative.

A model that writes "POST ONE project, assert 1" has not disobeyed anything it can see: one
project is a perfectly sensible list test. The number 3 is only meaningful if you know what
it is defending against, and that knowledge lived in another entry.

CORRECTION — SAME NIGHT, AND IT NARROWS THE MECHANISM RATHER THAN THE RESULT

I titled this "between entries" and that is wrong. The controlling comparison is tighter and
the tighter version is more surprising.

TestProjectListNegativeOffsetIsClampedHere lives in the SAME ENTRY as the paging test that
failed — projects_test.go, three sentences above it — and it carries its OWN eight-line
reason ("projects.go has its own handler, its own strconv parse and its own `offset < 0`
clamp ... Measured: with the task test in place and this one missing, the projects clamp
could be changed to assign 7777 and the whole suite stayed green"). That test HELD: CAUGHT on
both draws.

So within one entry, in one draw:

    test WITH its own reason, three lines up   -> CAUGHT
    test WITHOUT one, immediately below it     -> witness cannot fail, SURVIVED

The reason did not have to cross an entry boundary to fail to apply. It did not carry three
sentences.

    THE REASON MUST BE ATTACHED TO THE TEST, not merely present in the entry. Adjacency
    does not transfer it, and neither does a cross-reference.

That also explains the /tasks side without appealing to entries at all: its paging reason sits
immediately after both paging tests, attached to them. Every closure tonight that held had its
justification next to it; the one that failed is the one whose justification was a pointer.

The entry boundary is still real — it is what _promise_gap measures, and the config guard this
morning genuinely failed to cross one. But it is not what happened here, and publishing the
wider mechanism would have had me solving the wrong problem: moving reasons between entries
rather than attaching one to every test that needs it.

THE PROMISE GAP IS THE SAME FAMILY, ONE LEVEL COARSER

_promise_gap.py exists because taskapipro's config_test entry demanded a guard its config.go
entry never promised, and the model — reading one entry at a time — wrote a test the
implementation had never been asked to satisfy. Same mechanism here, one layer up:

    A PROMISE STATED IN ONE ENTRY DOES NOT REACH ANOTHER (this morning's config guard, which
    _promise_gap now finds), AND A REASON STATED FOR ONE TEST DOES NOT REACH THE NEXT TEST
    (tonight's paging twin). Same failure, at two different granularities — and the finer one
    is the one that bites, because it looks like it should be safe.

THE FIX, and why it is not "repeat the sentence louder"

The projects entry now carries its own reason, and the reason is the MEASUREMENT rather than
the rule: what the previous draw actually wrote, why it could not fail, and that the twin
for /tasks caught the same mutations. Tonight already showed that explaining a trap better
does not always work (healthz) — so what is stated here is not "be careful", it is "this
exact test was written last time and defended nothing".

Unverified. The next taskapipro draw answers it, and the answer is interesting either way:
if the reason works, spec reasoning is a per-entry cost that has to be paid in each entry;
if it does not, then a quantity that must be exact needs a different mechanism entirely.


CAN THIS BE AUDITED? MEASURED, AND THE ANSWER IS NOT YET

The obvious follow-up is a check for tests whose justification is a POINTER — "for the same
reason", "as above", "identical to the task version". Ran it over all 25 specs: 10 hits, and
the two shortest, read in full, are both fine.

    taskflow TestProjectGetReturns200 (60 chars, "for the same reason") — the cross-reference
    is to WHY it needs its own test, and the test itself is fully specified: "POST a project
    FIRST, GET /projects/{id}, assert ONE thing: rec.Code == http.StatusOK. Decode nothing."
    taskapi TestDeleteProjectMissing ("exactly as above") — refers to test SETUP structure,
    not to an invariant's justification.

And the check cannot separate the failure from the success it sits next to: the projects
CLAMP test cross-references too ("the task test of the same name") and HELD, because it also
states its own measured reason. Cross-referencing is not the defect. Cross-referencing
INSTEAD OF is.

So the generic scan has poor precision and its yield here is zero. What actually distinguishes
the one that failed is narrower: a test whose assertion is a COUNT, where a smaller setup
produces a number that is ALSO correct. "POST ONE project, assert 1" is right for a list test
and blind for a page-size test, and only the second reading needs three items.

I am not building that detector from one instance. Twice tonight a tool generalised from a
single case reported confidently about the wrong population — the probe classifier's
hardcoded name list and the route auditor's three drafts — and this would be the same move.
Recorded so the next occurrence has a first data point to join, rather than a tool built on
this one.
