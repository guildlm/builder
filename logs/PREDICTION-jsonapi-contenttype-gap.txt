PREDICTION — turning a convention into a contract (jsonapi's Content-Type)
==========================================================================
2026-07-25, before the edit.

NOT A HOLE — A SPEC GAP, which is a different thing and worth being precise about
  Five services set `Content-Type: application/json` and none of their specs asks for it.
  Dropping the header leaves every suite green. That is not an undefended promise: there
  is no promise. The model writes the header because that is what a JSON handler looks
  like, and nothing in the project requires it, tests it, or would notice if a different
  sampling temperature stopped producing it.

  The fix is a spec line, and the reason is not "implicit means broken" as a rule. It is
  that the alternative is depending on a model's taste and calling it a contract.

  jsonapi is chosen because it is the cheapest verifiable case: 4 files, greened in 57
  seconds with ZERO escalations, so the base alone should do it and a red result would be
  informative rather than ambiguous.

THE EDIT — state the promise AND name the test, which is the whole lesson of the day
  The spec already says "responds with JSON ... and Content-Type application/json" in the
  main.go purpose, so the PROMISE exists — what is missing is a named test. That makes
  this a weaker case than I first described: closer to the mirrored-route holes (promise
  stated, test unnamed) than to a true spec gap. Recorded as a correction to my own
  classification before the run rather than after it.

      TestContentTypeJSON: POST a valid message and assert the RESPONSE header
      Content-Type is exactly "application/json" — read it with
      res.Header.Get("Content-Type").

PREDICTION
  1. TestContentTypeJSON is written and passes.
  2. The build greens with the BASE alone, no fleet. jsonapi did 2 rounds / 0 escalations
     with the fleet, so the fleet was never the reason it worked.
  3. `drop Content-Type` flips SURVIVED -> CAUGHT, graded against the unedited artifact.
  4. The three closures already in this artifact family stay closed — specifically
     jsonapi's invalid-JSON 400 stays CAUGHT.

  (2) is the interesting one. If the base alone greens it, then the fleet was carrying the
  larger specs and nothing else, which sharpens the size finding: the constraint is not
  "small specs need the fleet less", it is "small specs do not need it at all".

===========================================================================
GRADED — one real result, and one error of mine that the grading caught.

  RUN: BASE ALONE (no fleet), 94 seconds, 3 fix rounds, rc=0, score 3/3.

  1. TestContentTypeJSON written and passes.  HELD — and written correctly:

         contentType := rec.Header().Get("Content-Type")
         if contentType != "application/json" { ... }

     It asserts the RESPONSE header, in the httptest-recorder idiom that matches the code
     it wrote, rather than the `res.Header.Get` wording the spec used for a live response.
     My first grep looked for the spec's phrasing, found nothing, and briefly suggested the
     model had tested the request header instead. The test was right; the search was wrong.

  2. The BASE ALONE greens it.  HELD — 94s, three rounds, no fleet, no escalations.
     This is the result worth keeping. Every closure so far ran the three-member fleet, so
     none of them could separate "the fleet helped" from "the fleet was along for the
     ride". On a four-file spec it was along for the ride. The size finding sharpens:
     small specs do not need the fleet AT ALL; the fleet is what carries the large ones,
     and on those it still is not enough (tasks-api, taskflow).

     ⚠️ COUNTED CONSISTENTLY AFTERWARDS, because "files" had been used loosely — sometimes
     spec entries, sometimes implementation .go files. By SPEC ENTRIES:
         jsonapi     3   GREEN, base alone, 94s
         shortener   7   GREEN, fleet, 891-1351s
         ratelimit   7   untested
         usersapi    8   untested
         tasks-api   8   RED, fleet, 3100s
         taskflow   14   RED, fleet, twice
     The boundary sits between 7 and 8 spec entries. Implementation-file count does NOT
     separate them — tasks-api and shortener both have five — so the variable is how much
     the spec asks for, not how much code results.

  3. "The mutation flips SURVIVED -> CAUGHT."  VOID — it was ALREADY CAUGHT.
     jsonapi was never one of the five Content-Type survivors. The sweep says so plainly:
         jsonapi CAUGHT · kvservice CAUGHT · ratelimit SURVIVED · shortener SURVIVED
         taskflow SURVIVED · tasks-api SURVIVED · usersapi SURVIVED
     and the unedited artifact already asserted the header at main_test.go:31. I picked
     the target from memory instead of re-reading the sweep output, and spent a run adding
     a second assertion for a promise that was already defended.

  WHAT IT COST AND WHAT IT DIDN'T
    94 seconds and a redundant named test in one spec. Nothing was broken: the build is
    green, the assertion is correct, and the promise is now stated twice instead of once.
    The cost is that the spec is slightly noisier for no defensive gain.

    The lesson is small and exact: the before-table is not optional even when the target
    "obviously" belongs to a known list. Every closure that worked today was graded against
    a control FIRST; this is the one where I skipped that step, and it is the one that
    turned out to be aimed at nothing. The discipline caught it — one grep of the sweep
    output at the start would have caught it sooner.
