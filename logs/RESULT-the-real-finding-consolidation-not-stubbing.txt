THE MECHANISM, RESTATED CORRECTLY
Not "entry order causes the stub". The accurate statement, which fits all five pairs and all three
specs:

    THE FIRST-GENERATED FILE OF A PAIR ABSORBS THE PACKAGE'S CONTENT.
    Reordering changes WHICH file absorbs it. It does not make the model split the content.

    store.go first  -> store.go takes implementation + interface + sentinels · memory.go = 14 bytes
    memory.go first -> memory.go takes implementation (+ sentinels, + interface on taskapipro)
                       · store.go is thinned to whatever survives

    Go accepts either, because a package does not care which file holds what — which is the
    29 July finding, and it is why nothing in the pipeline objects in EITHER direction.

SO WHAT IS THE FIX WORTH? Honestly, per spec:
    ledger      IMPROVEMENT. memory.go goes 14 bytes -> 2373 with 7 methods; store.go keeps its
                interface and loses only models.* references A had used. Net: a whole missing
                implementation becomes a complete one.
    workapi     PARTIAL. memory.go 14 -> 1769 with 5 methods; store.go keeps the interface but
                LOSES the two sentinels its entry names. A real regression traded for a bigger gain.
    taskapipro  NO GAIN. 14-byte file either way — only its name changes. Reverted at 01:55.

    ⚠️ I PROMOTED THIS AS "the fix is free". It is not free. It is a trade whose sign differs by
    spec, and I did not know that until I looked at the second file — six hours after the first pair
    and forty minutes after declaring three-for-three.
