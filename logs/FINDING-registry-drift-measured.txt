FINDING — how much of the mutation registry survives a regeneration
====================================================================
2026-07-25. Measured without regenerating, because brittleness is a property of the
PATTERN, not of the artifact.

THE QUESTION
  Two mutations were found expired against fresh usersapi/ratelimit trees and repaired by
  matching on shape. That leaves the obvious question — how brittle are the other 28? —
  and only two fresh trees to ask with.

THE METHOD
  Ask the matcher, not the artifact. The drift a regeneration produces is overwhelmingly
  RENAMING: a different receiver, a different field for the same map, a different local for
  the same slice. Apply those renames textually and see which patterns let go. Nothing has
  to compile; the only question is whether the matcher still matches.

THE FIRST NUMBER WAS WRONG BY THREE TIMES, AND THE REASON MATTERS
  First pass: 15 of 28 BRITTLE — over half the registry rotten. That number came from a
  rename list that mixed drift I had WATCHED HAPPEN with drift I invented, including
  `w` -> `rw` and `b` -> `bkt`. But `w` for an http.ResponseWriter is near-universal Go
  convention; a coder renaming it is not the drift this models. Splitting the list by
  evidence:

        survives observed    23/28   renames taken identifier-for-identifier from the real
                                     fresh usersapi tree (s->m, users->items, ok->exists,
                                     out->result)
        survives plausible   23/28   same class, invented words (tasks->entries) — adds
                                     nothing, which is itself informative
        survives all         13/28   includes the convention-pinned renames — inflated

  So the defensible figure is FIVE brittle, not fifteen. Acting on the first number would
  have meant rewriting two thirds of the registry to fix a fifth of it.

  This is the decompose-before-acting rule again, and it is the third time this week it has
  changed a conclusion rather than confirmed one. A brittleness score is only as honest as
  the drift fed into it, and the drift is the part nobody audits because it looks like
  setup rather than data.

THE FIVE, AND ONE OF THEM IS DELIBERATE
  BRITTLE  ledger      internal/store/memory.go   every credit lands
  BRITTLE  taskflow    store.go                   duplicate Task ID -> ErrExists (409)
  BRITTLE  taskapipro  internal/store/memory.go   ListTasks sorted by ID
  BRITTLE  walkv       store.go                   Delete removes the key
  BRITTLE  genericset  set.go                     Len returns the exact element count

  taskflow's is BY DESIGN and must stay: that file has TWO ErrExists guards (s.tasks and
  s.projects), so the matcher deliberately falls back to the registered literal to say
  which one it means. Renaming the receiver breaks it, and the alternative — matching by
  shape — hit both guards and silently voided the verdict. Brittle-and-precise beats
  robust-and-ambiguous when a file has siblings; the cost is real and is now recorded
  rather than discovered again later.

  The other four are ordinary name-pinning and are candidates for the same shape treatment.

TIERS ARE KEPT IN THE TOOL, NOT COLLAPSED
  All three rename tiers stay in _registry_drift.py with the unlikely one labelled "do not
  quote", so the inflated number cannot be produced again by accident and then cited.

REPAIRED — same session
=======================
      survives observed   23/28  ->  27/28

  The four ordinary name-pinnings were widened to match by shape:
      ledger      the += posting line, receiver and posting local widened (`balances` kept —
                  a regeneration renames `s`/`p`, not the field that names the invariant)
      genericset  `return len(<recv>.m)` — receiver widened, FIELD kept. Widening both would
                  have let it match some other method's `return len(...)`, and the count
                  test would then say NOAPPLY: one silent failure traded for another.
      walkv       the delete call inside the DEL-log anchor, `delete(<recv>.<field>, key)`
      taskapipro  the ListProjects boundary marker and the comparator, via the same
                  backreference that binds both indexes to one identifier

  The single remaining BRITTLE row is taskflow's, deliberately, for the sibling-guard reason
  above. Full suite re-run after the change: 29 CAUGHT / 0 SURVIVED, 29 of 30 applied,
  identical to before — which is the check that matters, because the last time I widened a
  matcher it silently voided a verdict and only the full re-run caught it.

  Note what did NOT change: the "survives all" tier went 13 -> 17, still far below 27. Those
  four extra failures are the convention-pinned renames (`w`, `b`) that I am deliberately
  not fixing, because tolerating them would cost the precision that keeps a mutation aimed
  at one site. The gap between the tiers is the honest cost of that choice, left visible.
