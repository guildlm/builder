FINDING — sweeping for holes a hand-run campaign could not have thought of
=========================================================================
2026-07-25, model-free. `_hole_hunt.py` over all 25 archived -v4 artifacts.

FINAL: four shapes, every site — 34 probes, 11 survivors, 6 genuine undefended promises.
  status code      3 genuine / 9      response header  1 genuine / 8 (+3 spec gaps)
  sort order       0 genuine / 6      error wrapping   2 genuine / 5

(The filename says status-code because that is the shape it started with; three more
followed and the sections below are in the order they were run, each with its own spec
check. The title is what the file is about; the name is where it began.)

The document is written in the order the work happened, so the first section's headline —
"two holes, only one of them counts" — is true of the first pass and superseded by the
totals above. Read on for how each shape was chosen, what it caught, and which survivors
turned out not to be holes at all.

WHY SWEEP AT ALL
  The teeth campaign reached 29 CAUGHT / 0 SURVIVED by choosing invariants to test one at
  a time. That number reads as "no holes left" and actually means "no holes left among the
  ones I thought to check". The difference is exactly the failure this project keeps
  naming, so: sweep. For every artifact, find a status-code write in the code, swap it for
  a plausible neighbour, ask whether the suite goes red.

RESULT: 9 artifacts had a mutable status write. 5 CAUGHT, 2 BASELINE-RED (verdict void —
tasks-api-min and tasks-api-noshadownudge are already failing, so nothing can be concluded
about them), and 2 SURVIVED.

SURVIVOR 1 — shortener. A REAL undefended promise.
  handlers.go:26 `writeJSON(w, http.StatusBadRequest, nil)` -> StatusNotFound. Suite green.

  The spec promises THREE ways to earn a 400:
      "400 on malformed JSON or when the url field is empty or fails url.ParseRequestURI"
  and it names ONE test for them:
      "TestShortenBadRequest: POST /shorten with `{\"url\":\"\"}` -> 400."
  That test exercises the empty-field branch at line 30. The malformed-JSON branch at line
  26 is promised in prose, has no test, and can return anything at all without a single
  number moving.

  Textbook shape for this project: an error path in a small HTTP spec, and a spec whose
  PROSE promises more than its NAMED tests cover. That is the spec-writer's half of the
  contract, and _named_test_audit cannot see it — the named test exists, so the audit is
  satisfied; it is the promise BEHIND the name that is short.

SURVIVOR 2 — taskflow. Real behaviour change, and NOT a hole worth the name.
  middleware.go:38 `rec := &statusRecorder{..., status: http.StatusOK}` -> StatusAccepted.
  The spec does mention it — "a Logging middleware (method, path, resolved status via a
  statusRecorder ...)" — so a handler that never calls WriteHeader would now be LOGGED as
  202 when it served 200.
  But the deviation is confined to log output. Defending it means capturing stdout in a
  test, which no spec here asks for and which would be a strange thing to require. Calling
  this an undefended invariant would inflate the count with something no reasonable suite
  defends.

  Recorded because the honest half of a sweep is the part you decline to claim. Two rows
  came back identical from the tool's point of view — SURVIVED, green build, real change —
  and only reading the SPEC separates a genuine hole from a curiosity.

WHAT TO DO WITH SURVIVOR 1
  It is a real gap and it is also exactly what the review-pass experiment needs
  (PREDICTION-review-pass-value.txt): a green build containing a known, spec-relevant
  semantic bug, with ground truth because the break is ours. So it gets used before it
  gets closed, and closing it means the spec naming a second test — the fix belongs to
  the spec, not to a gate, because "which of three conditions returns 400" is not
  something a compiler can name.

SCOPE: status codes only, one swap per artifact, first code-site only. This is the
cheapest sweep, not an exhaustive one. Other shapes — headers, sort order, error wrapping
— would each need their own pass, and the yield here (1 genuine hole in 9 probes after a
campaign that believed it was done) says those passes are worth writing.

SHAPE 2 — drop a response header. 4 more survivors, ONE more real hole.

  Dropping the `w.Header().Set(...)` line entirely is a sharper probe than changing its
  value: a strict equality assert can still catch a wrong value, but a test that never
  reads response headers cannot notice either way.

      kvservice   drop Content-Type   CAUGHT        (closed by hand in the campaign)
      ratelimit   drop Retry-After    CAUGHT
      shortener   drop Content-Type   SURVIVED
      taskflow    drop Content-Type   SURVIVED
      tasks-api   drop Content-Type   SURVIVED
      usersapi    drop Content-Type   SURVIVED
      (tasks-api-min, tasks-api-noshadownudge: BASELINE-RED, verdict void)

  Then the question that separates a candidate from a hole — does the SPEC promise it?

      taskflow   YES. "writeJSON(w, status int, v any) that sets Content-Type
                 application/json and encodes v". And the suite only ever sets
                 Content-Type on REQUESTS (req.Header.Set); nothing reads it off a
                 response. A promised header, defended by nothing. REAL HOLE.
      shortener  NO mention of Content-Type anywhere in the spec.
      tasks-api  NO mention.
      usersapi   NO mention.

  TWO SHAPES, TOTAL: 18 probes, 6 SURVIVED, 2 genuine undefended promises —
  shortener's malformed-JSON 400 and taskflow's response Content-Type. The raw survivor
  count overstates real holes by 3x, and only reading the spec closes the gap. That is the
  caveat from the first pass, now with a number on it.

  AND THE THREE NON-PROMISES ARE NOT NOTHING. A JSON API that never states its response
  Content-Type is a SPEC gap, not a test gap. This project's own law is that implicit
  means broken and naming is the spec-writer's job (_named_test_audit's METHOD notes), so
  the fix for those three is a line in the spec — after which a test can be named for it,
  and only then can teeth defend it. The sweep found them by breaking them, which is the
  only way an unstated promise ever surfaces.

EXHAUSTIVE PASS (--all-sites) — the first-site limit was hiding holes

  Both sweeps above stopped at the FIRST mutable site per artifact, which was a cost
  decision presented as a method. Probing every site: 23 probes, 9 SURVIVED, three of them
  new. Applying the spec test to the three:

  1. shortener router.go, StatusOK -> StatusAccepted on /health. REAL, and the cleanest
     hole found so far. The spec states it outright — `"GET /health" -> 200 "ok"` — and NO
     test in the artifact touches /health at all. A named behaviour with zero coverage;
     the endpoint could return anything.

  2. taskflow projects_handler.go, StatusBadRequest -> StatusNotFound on a MALFORMED body.
     REAL, with a caveat worth stating: the spec names TestMalformedJSON for the TASKS
     route ("POST truncated bytes -> 400") and names nothing equivalent for PROJECTS,
     whose named test covers only the empty-name validation branch. So it is not an
     unstated promise — it is a promise stated for one route and not for its twin. The
     model wrote the handler correctly both times; only one of them is defended.

  3. usersapi middleware.go, StatusOK -> StatusAccepted. The statusRecorder default again,
     exactly like taskflow's: log-only output, not worth calling a hole. Second time this
     exact shape has surfaced, which is itself informative — it is a recurring FALSE
     positive of this probe and should be recognised rather than re-litigated.

  ==> The cheap pass found 2 genuine holes; the exhaustive pass found 2 more. That is the
  argument against under-sampling stated as a number, and it lands on the same lesson the
  teeth campaign is built on: an absence of findings is not an absence of holes. The
  campaign's 29 CAUGHT / 0 SURVIVED was true of the mutations someone thought to write.

  RUNNING TALLY across both shapes, all sites: 23 probes, 9 survivors, 4 genuine
  undefended promises (shortener malformed-JSON 400, shortener /health, taskflow response
  Content-Type, taskflow projects malformed-body 400), 2 recurring log-only false
  positives, 3 behaviour changes the spec never asked for (which are SPEC gaps, not test
  gaps).

SHAPE 3 — reverse a sort comparator. SIX sites, ZERO holes.

  TEETH.md already fixes the form: deleting a `sort.Slice` catches only probabilistically
  (the unsorted order depends on Go's map-iteration randomness), so an order invariant is
  probed by REVERSING the comparator, which fails every run or never.

      logstats     stats.go   reverse sort by Path       CAUGHT
      priorityqueue pq.go     reverse sort by Priority   CAUGHT
      taskflow     store.go   reverse sort by ID         CAUGHT
      tasks-api    store.go   reverse sort by ID         CAUGHT
      usersapi     store.go   reverse sort by ID         CAUGHT
      tasks-api-noshadownudge                            BASELINE-RED (void)

  Every one defended. A shape that yields nothing is a result, not a wasted pass: sort
  order is exactly the invariant the campaign hardened by hand (three of these are
  registered teeth mutations), and an independent sweep agreeing with the registry is the
  cross-check that registry was missing.

  THE PATTERN NEEDED FIXING FIRST, and the fix is the third instance of the same mistake
  in one day. The comparator regex was anchored to the whole line — `^\\s*return X[i].F <
  Y[j].F$` — and five of the six comparators in the corpus are written INLINE:
      sort.Slice(out, func(i, j int) bool { return out[i].ID < out[j].ID })
  So the first run of this shape probed ONE site of six and reported a clean sweep. In a
  shape added specifically to fix under-sampling. Widened to a substring match (only the
  matched text is rewritten, so the flip stays unambiguous), and the count went 1 -> 6.

  ==> Across three shapes, all sites: 29 probes, 9 survivors, 4 genuine undefended
  promises, and one shape with no holes at all. The sweep is now cheap to extend and
  bounded by which shapes someone thinks to write — the same limit the hand campaign had,
  moved up one level, and worth saying plainly rather than letting the tool imply
  completeness.

SHAPE 4 — unwrap an error (%w -> %v). The sharpest probe here, and the best yield.

  `fmt.Errorf("...: %w", ErrX)` -> `%v` leaves the message BYTE-IDENTICAL and breaks
  errors.Is. A test that compares the error string still passes; only a test that actually
  calls errors.Is notices. So a SURVIVED here is not merely a missing test — it is a test
  that checks the wrong thing, which no amount of reading the suite for coverage reveals.

      logstats    parse.go    %w -> %v   CAUGHT
      taskflow    models.go   %w -> %v   SURVIVED
      tasks-api   task.go     %w -> %v   SURVIVED
      tasks-api-min / -noshadownudge     BASELINE-RED (void)

  Both survivors are spec-promised, checked rather than assumed:
      taskflow   "errors.Is: ErrNotFound, ErrExists, ErrValidation" — named explicitly.
      tasks-api  mentions errors.Is twice.
  So both are REAL: the spec asks for sentinel errors to be identifiable by errors.Is, the
  implementation wraps them correctly, and nothing would notice if it stopped.

  YIELD BY SHAPE, all sites:
      status codes      3 genuine holes / 9 probes
      response headers  1 genuine / 8 probes  (+3 spec gaps)
      sort order        0 genuine / 6 probes  (fully defended)
      error wrapping    2 genuine / 5 probes  <- highest rate
      TOTAL            34 probes, 11 survivors, 6 genuine undefended promises

  Error wrapping being the best yield is not an accident of this corpus. The other three
  shapes change something a test can SEE by accident — a status code, a header, an order.
  This one changes nothing observable except through the one API that checks it, so a
  suite passes unless someone deliberately wrote errors.Is. It is the shape most likely to
  be undefended and the least likely to be noticed, which is the definition of where a
  mutation sweep earns its keep.

---------------------------------------------------------------------------
EVERY WRAP, NOT ONE PER FILE — "defended" turns out to be a property of a SITE

  Shape 4 originally probed the first `%w` in each file. Probing every one changes what
  the table says:

      logstats   parse.go   ErrBadLine      CAUGHT ×4            fully defended
      taskflow   models.go  ErrValidation   SURVIVED, CAUGHT, CAUGHT   HALF defended
      tasks-api  task.go    ErrInvalidTask  SURVIVED             (ErrNotFound: 4 asserts)

  taskflow's models.go wraps ErrValidation three times and the suite defends two of them.
  One-site probing would have reported whichever it hit and called the file settled — and
  which one it hits is alphabetical accident, not evidence.

  tasks-api is the sharper case because it looks BETTER than it is. Its tests call
  errors.Is four times, which reads as a suite that takes sentinel errors seriously. All
  four check ErrNotFound. The spec promises two sentinels; the second, ErrInvalidTask, has
  no errors.Is assertion anywhere. A reviewer scanning for "does this suite use errors.Is"
  gets yes, and the answer is only half true.

  ==> The unit of defence is a SITE, not a file and not an API. "The suite tests errors.Is"
  is not a fact about a suite; it is a fact about one sentinel in one place. Any audit that
  aggregates above that level — including a human reading for coverage — will report the
  defended half and stop.

  This is the same shape as the shortener hole one level down: there, a spec NAMED a test
  and the promise behind the name was broader than the test. Here a suite USES the right
  API and the promise behind the API is broader than the assertions. Both are invisible to
  anything that checks for presence rather than for reach.
