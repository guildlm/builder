📌 THE CONSEQUENCE, AND IT IS THE REASON THIS IS A RESULT AND NOT A NOTE
BOTH queued experiments are UNINFORMATIVE on a process whose declarer already writes the
correct name — and pid 77977 is such a process.

  THE SPEC FIX (`var ErrX`). Its mechanism is that `_required_decls` goes 0 -> 5, so the
  generation gate REJECTS a models.go candidate missing any of the five. On this process the
  model writes all five unaided. Nothing is missing, so nothing is rejected, so THE GATE CANNOT
  FIRE. The pre-registered PRIMARY endpoint is not merely unlikely here — it is unreachable by

  THE API-BLOCK FIX (shipped today). Its endpoint is "does internal/api reference a name that
  models declares". The consumer's choice of `ErrInsufficientFunds` is the single most stable
  thing in this corpus — 25 of 25 across a month and three processes. When the declarer ALSO
  writes that name, the endpoint passes whether or not the consumer can see the block. Pass
  without discrimination is not evidence.

  SO: the informative processes are the ones that ABBREVIATE or OMIT. Running either experiment
  on a process that already succeeds spends an hour of GPU to observe a foregone conclusion.

⏭️ THE DESIGN THAT FOLLOWS, and the killed draw is what makes it cheap
models.go is file 4 of 19 and took ~8 minutes. A PROBE DRAW that generates only as far as
models.go classifies a fresh server process for a fraction of a full draw's cost:

    restart server -> generate to models.go -> read the sentinel
        writes the long name   -> uninformative process, restart and re-probe
        abbreviates or omits   -> run the paired experiment ON THIS PROCESS

⚠️⚠️ THIS IS SELECTION, AND IT MUST BE DECLARED IN ADVANCE OR IT IS CHERRY-PICKING. Choosing a
process by its baseline makes the result CONDITIONAL: "among processes whose declarer gets the
name wrong, does the fix help?" That is the honest claim and it is also the population the fix
exists for — a fix for a defect can only be tested where the defect occurs. What it is NOT is
an estimate of how often the defect happens; the archive already answers that (36/36/28 over 25
ledger trees) and the probe must never be used to re-estimate it, because probes that come back
"long" would be discarded.
    The count of DISCARDED probes must therefore be logged, every one, or the selection becomes
    invisible and the conditional claim silently reads as an unconditional one.
