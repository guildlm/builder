THE PATTERN THAT KEEPS APPEARING — MIRRORS
  Of the 21, at least eight are a guard whose IDENTICAL TWIN on a neighbouring route has a
  test:

      tasks-api    invalid id -> 400        Get, Update, Delete: none tested
      tasks-api    malformed body -> 400    Create tested, Update not
      shortener    404                      Redirect tested, Stats not
      taskflow     404                      Get tested, Delete not
      shortener    400                      empty url and malformed JSON tested,
                                            url.ParseRequestURI failure not — a THREE-way
                                            promise with two tests

  taskflow's is the sharpest illustration. The spec promises "Delete (204 or 404)" and
  names TestDelete as "POST a task FIRST, DELETE it -> 204, then GET it -> 404". That test
  asserts a 404 — from GET. Delete's own 404 has never been requested. The promise looks
  covered, in a test named for the very route that does not defend it.

  This is the same lesson as the clamp layers found this morning: an invariant implemented
  in N places needs N tests, and the one place with a test is what makes the other N-1 look
  finished.

WHAT THIS SAYS ABOUT THE METHOD
  Three separate things had to be true for a hole to be visible today, and each was false
  somewhere in this corpus:
     the mutation must APPLY          (47 refusals, fixed)
     the mutation must be OBSERVABLE  (6 of 15 boundary survivors were not)
     the site must be REACHABLE       (22 of 48 survivors are not)
  A hole hunter that checks only the first reports 48. One that checks all three reports
  21. The difference is not tidiness — it is five specs almost edited to defend behaviour
  that no input can produce.
