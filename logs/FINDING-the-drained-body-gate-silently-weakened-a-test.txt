FINDING — the drained-body gate repaired a test by deleting what it tested, and nothing failed
===============================================================================================

Caught 11:35 on 29 July, live, in workapi-v5's fix round 1, by diffing the as-drawn snapshot
against the tree after the deterministic pass. The test still passes. It tests strictly less
than it did.

THE TWO CASES, SAME GATE, SAME FILE, SAME ROUND

TestCreateDuplicate — HANDLED CORRECTLY
  as drawn:  req := NewRequest(POST, body)
             req.Header.Set("Authorization", "Bearer secret")     <- mutation BEFORE both
             ServeHTTP(rec, req)      201
             rec = NewRecorder()
             ServeHTTP(rec, req)      409          <- second serve, body drained
  repaired:  ... req = NewRequest(POST, body)
             req.Header.Set("Authorization", "Bearer secret")     <- REPLAYED. correct.

TestCreateUnauthorized — SILENTLY WEAKENED
  as drawn:  req := NewRequest(POST, body)                        <- no token
             ServeHTTP(rec, req)      401   (no token)
             req.Header.Set("Authorization", "Bearer wrong")      <- mutation BETWEEN serves
             rec = NewRecorder()
             ServeHTTP(rec, req)      401   (WRONG token)
  repaired:  ServeHTTP(rec, req)      401   (no token)
             req.Header.Set("Authorization", "Bearer wrong")      <- now applies to the OLD req
             rec = NewRecorder()
             req = NewRequest(POST, body)     <- INSERTED HERE, AFTER the mutation, no header
             ServeHTTP(rec, req)      401   (no token AGAIN)

The rebuild was inserted AFTER the mutation instead of replaying it. "Bearer wrong" is now
set on a request that is discarded one line later, and the second half of the test repeats
the first half.

    The test's two cases were "no token" and "WRONG token". It now checks "no token" twice.
    Both expect 401, so the loss produces no failure and no output. Nothing announces it.

WHY THE DIFFERENCE, AND IT IS THE MUTATION'S POSITION
In TestCreateDuplicate the Header.Set precedes BOTH ServeHTTP calls, so replaying it onto the
rebuilt request reproduces the author's intent exactly. In TestCreateUnauthorized the
Header.Set sits BETWEEN the two serves — it is not setup, it is the second case's INPUT. A
gate that collects "mutations applied to req" and replays them before the next serve has no
way to distinguish those two roles from the AST alone, and here it did the safe-looking
thing: it left the statement where it was and rebuilt after it.

THIS IS THE EXACT FAILURE THE GATE'S OWN DOCSTRING CLAIMS TO PREVENT

    "the rebuild REPLAYS the mutations the author applied — without which the repaired test
     loses its req.Header.Set("Authorization", ...) and fails 401 instead of 400, trading
     one silent breakage for another."

It anticipated losing the header and producing a WRONG ANSWER. What happened is worse and
quieter: the header was lost and the answer stayed RIGHT, because both branches of this
particular test expect the same status code. The docstring's failure mode is loud. This one
is not.

AND IT IS THIS PROJECT'S FOUNDING OBSERVATION, INSIDE ITS OWN REPAIR TOOL
A green suite that no longer defends what it defended yesterday. The campaign has spent a
week finding that in MODEL-WRITTEN tests; this instance was written by a deterministic gate
built to make tests correct, and it is invisible to every instrument here — mutation testing
grades the tests that exist, and this test exists and passes.

⚠️ WHAT I HAVE NOT ESTABLISHED. I have not read freshreq.go's replay logic closely enough to
say whether this is a mis-ordering bug with a small fix, or a genuine limit of AST-level
repair. The distinction matters and I am not asserting it. What is established is the
before/after on this artifact and that the resulting test is weaker.

⚠️ AND IT DOES NOT TOUCH THE Delete-404 RESULT. That closure is byte-identical to as-drawn
and to chain2, verified separately after this same round. TestCreateUnauthorized is a
different test in the same file.

NEXT — and it belongs with the other src/ work, after the draws drain:
  1. Check how many other artifacts have a Header.Set BETWEEN two serves — the same shape
     would be weakened the same way, silently, corpus-wide.
  2. The gate should REFUSE rather than repair when a mutation sits between two serves, on
     the same principle already written into the paging-gate design: refuse where the
     rewrite cannot be known correct.


WHY IT SLIPPED PAST THE CANDIDATE GUARDS (11:37) — they check declarations, not behaviour
==========================================================================================
Round 1 of this same run also produced:

    rejected fix candidate 1: drops failStore — still used, no sibling declares it

So the loop DOES reject destructive model edits. The guard (src/builder.py:4863) refuses a
candidate that removes a top-level declaration still referenced elsewhere. It works, and it
fired on this very artifact minutes after the weakening landed.

    It catches losses the COMPILER would notice — a dropped declaration leaves an
    `undefined:` behind. It cannot catch a loss with no compile signature.

TestCreateUnauthorized lost neither a declaration nor an import. It kept every symbol, kept
compiling, and kept passing. What it lost was the DIFFERENCE between its two cases, and
nothing in the toolchain has an opinion about that. The guards are a presence check on
declarations; the weakening was a change in what the test exercises.

    Same distinction as the campaign's own law, one level up. Presence of a named thing is
    checkable and defended. What a test actually distinguishes is neither.

AND THE REPO ALREADY LEARNED TODAY'S OTHER LESSON, IN THIS FUNCTION'S DOCSTRING
why_dirty exists because rejections used to be logged without saying WHICH rule fired:

    "a rejection landed in the same round as an `undefined: failStore`, the two looked
     consistent, and I was one inference from crediting the rule I had just written.
     Consistent is not proof."

That is the shape this session has hit repeatedly — an answer that is right about its own
query and wrong about its subject — already written down, in the code, before today. The
remedy adopted there is the one that has worked here all day: make the output name its
subject.

⚠️ THIS IS NOT A CRITICISM OF THE CANDIDATE GUARDS. They are doing what they claim, and one
of them rejected a genuinely destructive edit in the same round. The gap is that NOTHING in
the loop is positioned to notice a test that still passes while distinguishing less, and no
addition to a candidate guard would find it — the weakening was introduced by a DETERMINISTIC
pass that runs before candidates exist.


CORRECTION TO THE ADDENDUM ABOVE (11:40) — the guard is a PREFERENCE, then a REPAIR
====================================================================================
I wrote "the loop DOES reject destructive model edits". The full log sequence is more
interesting and my wording was too strong:

    rejected fix candidate 1: drops failStore — still used, no sibling declares it
    rejected fix candidate 2: drops failStore — still used, no sibling declares it
    best-of-N fix: no clean candidate; using the first of 2
    restored failStore into fix candidate — the rewrite dropped what it still calls

BOTH candidates were rejected, and the loop then USED ONE ANYWAY — "no clean candidate;
using the first of 2" — and afterwards repaired the specific loss it could name, splicing
failStore back in.

So the guard is not a veto. It is a ranking, and when nothing ranks clean the loop proceeds
with a dirty candidate and patches what it has a rule for. That is defensible engineering —
refusing outright would strand the round with no progress at all — but it means the phrase
"rejected" in the log does not imply the candidate was discarded, and I read it as if it
did.

    Two rejections and a use, on adjacent lines. I quoted the first line and inferred the
    outcome, which is the same mistake as reading a round header and inferring how the run
    ended.

WHAT SURVIVES OF THE ADDENDUM. The substance is unchanged and slightly strengthened: the
loop's protections cover losses it has a NAMED RULE for — a dropped declaration, restored by
name — and nothing else. TestCreateUnauthorized's weakening has no rule, so it was neither
rejected nor repaired nor logged. The gap is not that a veto failed; it is that no rule
exists for the shape.
