FINDING — "assert ONLY the length" is the instruction that let the setup count drift
=====================================================================================

Measured 29 July ~10:18 across THREE artifacts, chosen because the structural-vs-quantity
law predicted they would differ. They do, and the spec text explains it exactly.

The previous finding said quantities are the fragile class because nothing holds them in
place. This says WHAT would have held this one, and which sentence removed it.


THREE QUANTITY-BOUND WITNESSES, AND WHAT THEIR SPECS ASKED FOR
---------------------------------------------------------------

lrucache TestEvictsLeastRecentlyUsed        capacity 2, 3 Puts       CORRECT
  spec gives LITERAL CODE:
     "c := New(2); c.Put("a", 1); c.Put("b", 2); c.Put("c", 3); // capacity 2, so "a"
      ... is evicted. assert Get("a") ok false; Get("b") ok true; Get("c") ok true;
      assert c.Len() == 2."
  The assertions NAME three keys. You cannot assert about "c" without having Put "c".

taskflow TestListSorted                     seeds 3, asserts 3       CORRECT
  spec describes PER-ITEM assertions:
     "Assert len(got) == 3 AND the ids come back ASCENDING: got[0].ID == "1",
      got[1].ID == "2", got[2].ID == "3"."
  Again the assertion names each item. Three named ids require three seeded items.

taskapipro TestListDefaultsToTheConfiguredPageSize   seeds 1, asserts 2   WRONG
  spec restricts to a BARE COUNT:
     "POST THREE tasks, then GET /tasks with NO limit parameter and assert,
      AS THIS TEST'S ONLY ASSERTION, that EXACTLY 2 come back."
  The assertion names nothing. `len(resp) != 2` is satisfiable — or not — by any store
  contents whatsoever, so nothing in the test's own text requires three POSTs.

    A per-item assertion makes the setup STRUCTURAL: the item must exist to be named.
    A bare count assertion leaves the setup FREE, and free is what drifted.

That is the previous finding's mechanism, and it converts it into a spec-side repair
instead of a gate.


THE UNCOMFORTABLE PART: THE RULE THAT BROKE IT IS A RULE I ADDED ON PURPOSE
---------------------------------------------------------------------------
"as this test's ONLY assertion" is not sloppiness. It is the fix for the shortener defect
recorded this week — a draw asserted on a SETUP STEP, expected something other than 301,
and the suite went red against a correct handler. The remedy was to make each test assert
ONE outcome and forbid the rest.

Both rules are good advice. Together they are a contradiction:

    focus rule    "assert ONE outcome, nothing else"      -> removes per-item assertions
    witness rule  "the assertion must name the items"     -> requires per-item assertions

and the focus rule won, because it is the one written into the entry. The paging witnesses
were weakened by a discipline introduced to stop a different failure, and nothing announced
the trade because each rule is individually correct and they live in different entries of
different specs.

    Two spec rules, each measured and each right, whose intersection is a test that
    cannot fail.


THE GRADIENT, AND THE CHEAP FIX
--------------------------------
    literal setup code            lrucache    correct   strongest, least general
    per-item assertions described taskflow    correct   general, and cheap
    bare count + ONLY-assertion   taskapipro  wrong

The repair is to move the taskapipro twins one step up the gradient: keep the focus rule's
INTENT (do not assert on setup steps) while requiring the assertion to name what came back.

    instead of: assert, as this test's ONLY assertion, that EXACTLY 2 come back
    write:      POST ids "1","2","3"; assert the response holds EXACTLY the first two —
                len == 2, got[0].ID == "1", got[1].ID == "2" — and that "3" is absent.

That is still one outcome, still no assertion on a setup step, and it cannot be written
without three items in the store. It costs a sentence.

⚠️ THIS DOES NOT RETIRE THE GATE. NOTE-the-paging-seed-gate-has-a-precedent-and-a-trap.txt
still stands, for the reason its precedent gives: a nudge is not a gate, and this repair is
a nudge. The difference is that it is a nudge with a MECHANISM — it changes what the test
must contain rather than asking for a number — and it is testable in one draw against the
gate's several days. Do the sentence first; it may make the gate unnecessary, and if it
does not, the gate is better justified for having been tried.

⚠️ BOUNDS. Three witnesses, three artifacts, one draw each. The lrucache and taskflow rows
were checked BECAUSE the law predicted them, not gathered to support it — but they are
still only two confirmations, and neither is a paging test. The prediction that makes this
falsifiable: rewrite the taskapipro entry as above, redraw, and the seeds should become 3.
If they do not, the assertion shape is not what governs the setup and this is wrong.


ADDENDUM (10:47) — THE BOUNDARY: "ONLY ASSERTION" IS HARMFUL ONLY WHEN THERE IS A SETUP
========================================================================================
Found while preparing the workapi check, and it makes this finding usable instead of
alarming.

workapi's Delete-404 entry carries THE SAME PHRASE:

    "TestDeleteMissingReturns404 — on a FRESH router, DELETE /tasks/nope with a valid
     token — an id nobody created — and assert, AS THIS TEST'S ONLY ASSERTION, that the
     code is 404."

and that closure was CAUGHT on workapi-chain2. The draw wrote exactly what was asked: fresh
router, one DELETE, an auth header, one status assertion, nothing else.

WHY THE SAME PHRASE IS SAFE HERE
There is no setup quantity to free. The test seeds NOTHING — "an id nobody created" is the
whole precondition, and a fresh router satisfies it. A bare assertion cannot leave a seed
count unconstrained when the correct seed count is zero.

    taskapipro paging   ONLY-assertion + a bare COUNT over a SEEDED collection  -> drifted
    workapi Delete-404  ONLY-assertion + a STATUS on an EMPTY store             -> CAUGHT

THE RULE IS NARROWER THAN THIS FILE FIRST STATED
Not "never write ONLY assertion" — it is a good rule and it fixed a real shortener defect.
The failure mode is specific:

    An ONLY-assertion instruction is dangerous exactly when the assertion is a COUNT (or
    any aggregate) over a collection the test must SEED, because then the assertion is the
    only thing that could have pinned the seeding, and forbidding everything else unpins it.

Where the assertion is a status code, an error value, or anything on an empty store, the
phrase costs nothing and buys the focus it was written for.

AND IT PREDICTS THE WORKAPI RESULT FOR A REASON
FINDING-structural-closures-survive-redraws-quantities-do-not.txt puts Delete-404 in the
structural class and predicts it holds. This says the same thing from the spec side: there
is no quantity in that entry to lose. Two independent routes to the same prediction, which
is why the registered 85% is the least uncertain number in the pending list.

WHAT TO CHECK WHEN workapi-v5 LANDS
    func TestDeleteMissingReturns404  — present, in internal/api/router_test.go
    fresh router, no seeding
    req.Header.Set("Authorization", "Bearer secret")   <- the drained-body gate rebuilds
                                                          requests and freshreq.go REPLAYS
                                                          mutations for exactly this reason;
                                                          a rebuilt request that lost the
                                                          header fails 401, not 404
    assert rec.Code == http.StatusNotFound, and nothing else


FOURTH DATA POINT (11:04) — ratelimit, and it is the cleanest of them
=====================================================================
Checked by reading only, because a mutation sweep during generation steals CPU from the
critical path (learned the hard way ten minutes earlier).

ratelimit-v5 TestBucket:

    b := NewBucket(2, 1)                          // capacity 2
    if !b.Allow() || !b.Allow() { ... }           // the first TWO must be true
    if b.Allow() { t.Errorf("third Allow() should be false") }   // the THIRD must be false

Three calls against a capacity of two. seeds > bound, so it DISCRIMINATES: delete the
capacity check and the third Allow() returns true and the test fails. TestBucketCapAfterIdle
does the same again after a refill.

AND THE ASSERTIONS NAME EACH CALL BY POSITION — "the first two", "the third", "after idle:
1st", "2nd", "3rd". That is the per-item pattern, in a form that does not even involve a
collection: the ORDINAL is the item. You cannot assert about the third call without making
three calls.

    the running count

    lrucache   literal setup code, per-key assertions       3 puts / cap 2    CORRECT
    taskflow   per-item assertions on got[0..2].ID          3 seeds / 3       CORRECT
    ratelimit  per-ordinal assertions on the 1st/2nd/3rd    3 calls / cap 2   CORRECT
    taskapipro bare count, "ONLY assertion"                 1 seed  / 2       WRONG

Four quantity-bound witnesses, four artifacts. Every one whose assertion names the
individual items or ordinals got its count right; the only one that asks for a bare
aggregate got it wrong. That is now the strongest single pattern in the campaign, and none
of the three confirmations was drawn to support it — all three were checked because the law
predicted they would come out this way.

⚠️ STILL ONE FAILING CASE. Three corrects and one wrong is not a rate, and taskapipro is
also the only one of the four where the spec explicitly FORBIDS additional assertions. The
pattern and the prohibition are confounded in the only negative instance, which is exactly
why the falsification test in this file is the right next move: rewrite taskapipro's entry
to name the items and redraw. If the seeds become 3, the assertion shape is what governs.


CORRECTION AND SHARPENING (11:17) — IT IS THE SETUP INSTRUCTION, NOT THE ASSERTION SHAPE
=========================================================================================
A within-FILE control found by auditing every spec instruction that asks for an explicit
count. It corrects the mechanism this file has been claiming.

taskapipro/internal/api/router_test.go holds BOTH of these, same draw, same model:

  TestListLimit          spec: "POST TWO tasks FIRST with ids OUT OF ORDER — id "2" then
                                id "1""
                         drew: TWO POSTs, bodies id "2" and id "1".   COUNT CORRECT.

  TestListDefaults...    spec: "POST THREE tasks"
                         drew: ONE POST.                              COUNT WRONG.

Same file. Same generation. The instruction that ENUMERATED THE ITEMS got its count right;
the instruction that stated only a NUMBER did not. That removes the artifact-level confound
this file was carrying — it is no longer taskapipro-versus-lrucache, it is two entries eight
lines apart in one file.

AND THE ASSERTIONS ARE NOT WHAT DID IT. TestListLimit's spec also asks for a first assertion
block — decode into `all` of length 2 and assert all[0].ID == "1", all[1].ID == "2". THE
DRAW DROPPED THAT ENTIRELY and went straight to the ?limit=1 request. So the per-item
assertions were NOT written, and the setup was STILL correct.

    What pins the setup is naming the items in the SETUP INSTRUCTION.
    Per-item assertions are a separate thing, and they can be dropped independently.

WHAT THIS CORRECTS. The section above says "a per-item assertion makes the setup
structural". That was the right family and the wrong member. The presence that matters is in
the instruction, not in the assertion — and TestListLimit is the case that separates them,
because it has one without the other.

THE REPAIR GETS CHEAPER AND MORE DIRECT
Earlier this file proposed rewriting the assertion to name what came back. The better repair
is one clause earlier in the sentence:

    instead of:  POST THREE tasks
    write:       POST THREE tasks with ids "1", "2", "3"

That is what TestListLimit already has and what taskflow, lrucache and ratelimit all have in
their own forms. It leaves the ONLY-assertion rule untouched, which matters because that rule
was fixing a real shortener defect and I would rather not trade one for the other.

⚠️ AND IT RE-OPENS A CONFOUND I HAD CLOSED. lrucache, taskflow and ratelimit all enumerate
their items AND assert per-item, so they cannot separate the two. TestListLimit is the ONLY
instance where the enumeration appears without the assertions, and it comes down on the side
of the enumeration. One instance. The falsification test should now vary the SETUP CLAUSE
alone — add ids to taskapipro's paging entries, change nothing else, redraw.


COUNTEREXAMPLE (11:19) — A BARE NUMBER THAT LANDED, AND WHAT IT COSTS THE LAST TWO SECTIONS
============================================================================================
Went looking for a counterexample rather than another confirmation, and found one on the
first broad sweep of the specs.

    specs/taskapi.yaml:125
        "TestListSorted: Create two tasks, then List -> id-sorted."

A BARE NUMBER. No ids enumerated, no per-item assertion requested, one clause long. The
draw wrote it correctly: two CreateTask calls with ids "2" and "1", len == 2, and
got[0].ID == "1" && got[1].ID == "2" — assertions it was never asked for.

So the correction I committed twenty minutes ago — "what pins the setup is naming the items
in the setup instruction" — is FALSIFIED as a necessary condition. This entry names nothing
and the count is right.

AND IT DAMAGES THE WITHIN-FILE CONTROL I LEANED ON. TestListLimit's entry asks for ids OUT
OF ORDER and a sorted assertion. Sortedness is MEANINGLESS WITH ONE ITEM, so its count was
forced by what the test is about, not only by the enumeration. The control I called clean
had two live variables in it and I reported one.

THE THIRD CANDIDATE, WHICH FITS EVERYTHING SO FAR

    The count is right when the TEST'S SEMANTICS force it, and wrong when only the
    instruction states it.

    sortedness forces >= 2         taskapi TestListSorted, taskflow TestListSorted,
                                   taskapipro TestListLimit          all CORRECT
    eviction forces > capacity     lrucache                          CORRECT
    rate limiting forces > burst   ratelimit                         CORRECT
    paging forces nothing obvious  taskapipro x4                     ALL WRONG

Paging is the odd one out for a reason the spec itself spends six lines on: "the default is
20, so POST 25 and expect 20" is the natural reading, and with fewer items than the page size
a handler that ignores the setting returns everything, which also looks right. Nothing in the
IDEA of paging says the store must hold more than a page. Nothing in the idea of sorting or
eviction lets you get away with one item.

WHERE THIS LEAVES THE FILE — three candidate mechanisms, and the corpus separates none

    (a) assertion shape        per-item assertions pin the setup
    (b) setup enumeration      naming the items pins the setup
    (c) semantic forcing       the test cannot mean anything at the wrong count

(a) was weakened by TestListLimit dropping its assertions and keeping its count. (b) is
falsified by taskapi:125. (c) fits all nine instances and is also the least falsifiable of
the three, which is exactly why it should not be believed yet.

    Every artifact that got its count right had a test whose meaning collapses at the
    wrong count. That is a good story and it is the third good story today.

THE EXPERIMENT THAT SEPARATES THEM, and it is still one draw
Add ONLY the ids to taskapipro's paging entries — "POST THREE tasks with ids "1","2","3"" —
changing nothing else. Paging semantics still do not force three, so:
    count becomes 3  -> (b) survives, (c) is not necessary
    count stays 1    -> (b) is dead and (c) is the live explanation
Either way one draw settles it, and it is cheaper than the gate.
