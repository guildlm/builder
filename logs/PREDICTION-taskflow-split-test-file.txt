PREDICTION — the constraint is per FILE, not a per-spec budget
==============================================================
2026-07-26. Correcting a finding published one commit ago from a single observation.

WHAT I PUBLISHED, AND WHY IT WAS WRONG
  taskflow-errwrap wrote 17 of the spec's 20 named tests, dropping three including one I
  had closed the round before. I concluded "named tests compete for a budget" and recorded
  it as a general constraint. The corpus says otherwise:

      taskapipro   49 named   48 written
      taskapi      35 named   35 written
      ledger       32 named   32 written
      workapi      31 named   31 written

  Specs asking for 30-49 named tests get essentially all of them. There is no ceiling near
  20, so taskflow's loss is not a budget effect. Generalised from one run again, and again
  it fit the day's theme — trade-offs and limits — which is the kind of finding that gets
  waved through.

WHAT THE NUMBERS ACTUALLY SUPPORT — per TEST-FILE ENTRY
      taskflow      taskflow_test.go             13 named    <- dropped 3
                    projects_test.go              6
                    middleware_recover_test.go    1
      taskapipro    largest entry                 9 named    <- dropped 1
      tasks-api     largest entry                 8 named    <- dropped 1
      taskapi/ledger/workapi  largest entries   5-9 named    <- dropped 0

  13 in one entry is far outside anything else in the corpus, and all three dropped tests
  belong to that entry. The two specs with the largest entries elsewhere (9 and 8) each
  dropped exactly one. Nothing at 7 or below dropped anything.

  n is 6 specs and the pattern is suggestive, not established. What makes it worth acting
  on is that it is CHEAP TO ACT ON and the action is independently correct.

THE EDIT — split by subject, which is where these tests belonged anyway
  TestListProjectsSorted moves to projects_test.go: it POSTs projects and asserts the
  projects order, and it was in the tasks file only because that is where I anchored the
  insertion. The two paginate tests get their own pagination_test.go entry: they call
  paginate DIRECTLY with no HTTP and share nothing with the handler tests.

      taskflow_test.go   13 -> 10       projects_test.go   6 -> 7
      pagination_test.go  0 ->  2       middleware          1

PREDICTION
  1. All 20 named tests are written this run — no drops.
  2. reverse sort by ID is CAUGHT at BOTH sites again, since TestListProjectsSorted comes
     back.

  If tests drop anyway, the per-file story is wrong too and the honest position becomes

THE PER-FILE STORY DID NOT SURVIVE THE FULL CORPUS EITHER — 2026-07-26
=======================================================================
Measured all 24 specs instead of the 6 I had looked at, and the mechanism claim fails:

      spec         max named / test entry     tests dropped
      workapi              11                       0
      taskapi              10                       0
      taskapipro            9                       1
      tasks-api             8                       1
      taskflow             13                       3

  workapi carries ELEVEN named tests in one entry and drops nothing. taskapi carries ten
  and drops nothing. So "an entry above ~9 loses tests" is refuted by the two specs
  immediately below taskflow.

  The obvious next candidate was prose LENGTH rather than test count — a generation-length
  limit would be a plausible mechanism. It fails harder:

      ratelimit_test.go   5983 chars,  3 named   dropped 0   <- the LONGEST entry in the repo
      taskflow_test.go    5141 chars, 13 named   dropped 3
      service_test.go     4657 chars, 11 named   dropped 0

  The longest entry in the corpus drops nothing.

SO: I DO NOT KNOW WHY TASKFLOW DROPS TESTS
  Three hypotheses, three refutations, all from the same handful of runs: a per-spec
  budget, a per-file test count, a per-file prose length. This prediction said in advance
  that if the per-file story failed I would rather hold "taskflow drops tests and I do not
  know why" than fit a third explanation. That is now the position.

  The split still runs, and still stands on its own: TestListProjectsSorted belongs in
  projects_test.go because it tests projects, and the paginate tests share nothing with
  the handler tests. If the drop stops, that is an EMPIRICAL result about this spec, not
  a confirmed mechanism — and one spec improving is not evidence for a rule.
