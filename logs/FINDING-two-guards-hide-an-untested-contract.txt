FINDING — a property defended by redundancy, not by tests, is invisible to mutation testing
===========================================================================================
2026-07-27. Model-free. Reproduce: python _bound_probe.py "empty list"

THE HEADLINE
  taskflow's empty task list goes on the wire as `[]`. Two independent things make that
  true, and a single-site mutation cannot disturb either one alone:

      store.go       out := make([]Task, 0, len(s.tasks))   // never nil
      pagination.go  if offset >= len(items) { return []T{} }  // normalises nil away

  Measured, all four cells:

      mutation                         GET /tasks on an empty store
      ----------------------------     ----------------------------
      none                             []
      store make() -> var out []Task   []
      paginate >= -> >                 []
      BOTH                             null

  Neither mutation is observable. Together they are. So `_hole_hunt` reports the paginate
  flip SURVIVED, `_bound_probe` correctly reports it INERT, and both are right about the
  mutation and wrong about the property: the `[]` contract is undefended by any test. It
  holds because two guards happen to agree, and it will keep holding exactly as long as
  both keep being drawn.

  This is a structural limit of single-site mutation testing, which is the entire
  methodology of the hole hunt. A property with N redundant guards needs an N-site
  mutation to expose, and the sweep only ever flips one.

AND IT IS NOT HYPOTHETICAL — three artifacts have only ONE guard
  usersapi, tasks-api and taskapi have no paginate between the store and the encoder;
  their list handlers pass the store's slice straight to writeJSON. One line changed:

      usersapi   out := make([]User, 0, len(s.users))          -> var out []User
      tasks-api  out := make([]Task, 0, len(s.tasks))          -> var out []Task
      taskapi    out := make([]models.Task, 0, len(s.tasks))   -> var out []models.Task

  All three then answer `null` where they answered `[]`, and ALL THREE SUITES STAY GREEN.
  A client that iterates the response breaks; nothing in the corpus notices. Confirmed
  two ways per artifact: the wire body was read before and after, and the artifact's own
  suite was run on the mutant.

  taskflow is the control in the same table — identical mutation, INERT — which is what
  makes the diagnosis "redundancy" rather than "these three are badly tested".

  CENSUS across the six HTTP artifacts, with the evidence level marked, because half of it
  is a reading and today is the day that distinction kept mattering:

      usersapi    ONE guard   HOLE   measured — wire read before/after, suite run on mutant
      tasks-api   ONE guard   HOLE   measured — same
      taskapi     ONE guard   HOLE   measured — same
      taskflow    TWO guards  inert  measured — the four-cell table above
      taskapipro  TWO guards  inert  measured — probe through NewRouter(TaskService,
                                     ProjectService, logger); body stays [] on the mutant
      workapi     TWO guards  inert  measured — same, through NewRouter(svc, "secret",
                                     logger) with a Bearer header and a no-op enqueuer

  All six measured the same way. The prediction for the last two was read off service.go
  before the probes were written and both held, which is worth exactly as much as any
  confirmed prediction and no more: the two readings that were WRONG today looked just as
  solid before they were checked.

WHY NO TEST SEES IT — and the first answer was wrong
  The obvious explanation is the json-tag one: decoding cannot see it. Measured, that is
  only half true, and the half that is false matters.

      body     []T len  []T nil   reflect.DeepEqual(got, []T{})
      ----     -------  -------   -----------------------------
      []       0        false     true
      null     0        true      false

  So len() is blind, and DeepEqual against a non-nil empty slice DISCRIMINATES. A test
  that compared the decoded value against []T{} would have caught this without ever
  touching the raw body. (An earlier draft of this file claimed DeepEqual passes on both.
  It does not.)

  The real reason is simpler and worse: THE CORPUS NEVER LISTS AN EMPTY STORE. usersapi's
  TestListReturnsAll posts two users and asserts len == 2; every list test in every one of
  these artifacts populates the store first. The empty case is not weakly asserted, it is
  never reached. Two guards agree about a code path no test has ever executed.

  That changes what the closure has to say. "Assert the body is []" is not enough on its
  own — the test has to GET the list on a FRESH store, which no existing test does, and
  the spec has to say so explicitly or the model will populate it out of habit like every
  other list test in the file.

  The rule still stands for spec writing, now with a companion: a wire contract needs an
  assertion on the wire, AND the empty case is a case. Decoding is the second half of a
  round trip and a round trip is symmetric in exactly the mistakes that matter — but the
  assertion that never runs is beaten by no assertion at all only in that it is harder to
  notice.

WHAT IS NOT CLAIMED
  Nothing here says the three artifacts are wrong today; they are correct. The claim is
  that their correctness is unpinned, and the corpus has already shown that unpinned
  behaviour moves between draws — that is the whole finding behind the durability work.
  `make([]T, 0, n)` versus `var out []T` is exactly the kind of thing a regeneration
  changes for no reason at all.

  Nor is this a new mutation SHAPE for _hole_hunt yet. It was considered and deliberately
  not shipped: 12 sites in the corpus, and 3 of the 6 HTTP artifacts would report SURVIVED
  for the redundancy reason above. A shape whose survivors are majority-inert is how today
  started, and shipping one on the same day would be a poor lesson to draw.

HOW EXPOSED IS THE CORPUS TO WIRE-SHAPE DEFECTS GENERALLY
  Counted across ten HTTP artifacts: assertions on a raw JSON body, ZERO. The one raw-body
  assertion in the corpus is shortener's `/health` returning the plain text "ok". Three
  artifacts (jsonapi, taskflow, tasks-api) decode into map[string]any, which is what closed
  the json-tag holes — a map sees a renamed KEY because the key is data rather than a
  struct field. It does not see `[]` vs `null`, because that distinction survives into a
  decoded []any as nil-ness, and nothing checks nil-ness.

  So the corpus has exactly one instrument for wire shape (map decoding), it was added for
  one shape, and it happens not to cover this one.

NEXT — three spec closures, deliberately NOT made yet
  usersapi, tasks-api and taskapi each need an own-named test asserting the RAW body of an
  empty list is "[]". Held back on purpose: all three specs are queued in the Chain sweep,
  whose value is that FIVE specs get the SAME edit, and slipping a second edit into one of
  them would spoil the comparison. Queue them once the sweep is graded.
