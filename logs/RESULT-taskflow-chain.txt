  The tree is RED, and a red baseline voids every CAUGHT/SURVIVED verdict (this is the rule
  that cost four by-hand runs to learn). So _hole_closed cannot grade it, and repairing the
  artifact until it went green would have meant patching an IMPLEMENTATION bug and then
  claiming a verdict about the patched thing.

  is defended", because the artifact does not build green.

  reported "order string absent" — a false negative, recorded in advance as advisory, and the
  reason the mutation is the authority. A grep for an assertion's text is not a measure of
  the assertion.

WHY THE TREE IS RED — two defects, neither the closure's
  1. TestWireFieldNames, a TEST-authoring inconsistency. The spec says: "POST a task
     carrying a project_id, GET /tasks, and decode the array into []map[string]any". Those
     two halves are COUPLED — the array decode is correct only for the list endpoint. This
     draw took the second half without the first: it requests GET /tasks/1, which returns an
     object, and decodes into []map[string]any. Self-inconsistent, so it fails at runtime.
     taskflow-v4 deviates from the same sentence in the OTHER direction — GET /tasks/1 with
     a map decode — which is wrong against the spec but internally consistent, so it passes.
     The spec sentence is splittable, and both draws split it; only one split compiles into
     a passing test.
     ACTION: make the coupling un-splittable in the entry. Not done yet — taskflow is
     holding several queued closures already and they should land as one batch.
  2. TestProjectCreateInvalid: POST an invalid project returns 201 where 400 is required.
     An IMPLEMENTATION bug — the project handler does not validate. Unrelated to middleware.
