WHAT THE STRIP LINE MEANS, and it is the whole finding
memory.go's candidate in the A arm was stripped and what remained was FOURTEEN BYTES. So the
candidate consisted ENTIRELY of declarations store.go already had, and `strip_redeclarations` removed
every one of them. WHICH declarations they were is not recorded — see the correction below.

    The stub is not the model failing to write the file. It is the model writing SOMETHING the
    sibling already had, and the harness deterministically deleting all of it.

    ⚠️ WEAKENED 31 July, later the same day, by asking what evidence would establish the stronger
    claim. I wrote "the model DID write MemStore and its methods into memory.go". The 14-byte result
    proves only that EVERY top-level declaration in the candidate was one store.go already had — and
    that is equally consistent with the candidate containing a duplicate of the Store INTERFACE and
    no implementation at all. Both hypotheses strip to a bare `package store`.

    Nothing in the record separates them. `strip_redeclarations` logs no names; the trace records the
    response AFTER stripping (builder.py:5375, `response: code`, where code is already stripped); and
    the generation gate cannot arbitrate either, because sibling_decls had already emptied memory.go's
    demand, so there was no rejection to read.

    WHAT WOULD SETTLE IT: log the stripped NAMES, or trace the pre-strip candidate — a one-line
    change — then one draw of ledger-origorder. Until then the claim is "the candidate was entirely
    redundant with its sibling", which is what the evidence supports, and NOT "the model put the
    implementation in the right file".

The stripper's rule is "a sibling already declares it, so drop it here". It has no notion of which
file the PLAN gave the symbol to — although the harness computes exactly that, three functions away,
in `_required_decls`, and `_fill_empty_planned_files` exists solely to put the declaration BACK
afterwards. The harness creates this stub and then repairs it.

WHAT THIS CHANGES
    1. "The model cannot split a package" is wrong, and I have been repeating it for a week. Given
       the implementer's entry first, the model splits correctly — four draws for four, no stripping
       needed, both files right. This one does NOT depend on the retracted claim: it rests on the B
       arm's artifacts, which are on disk and were read directly.
    2. The remaining question is much narrower: why does the model, writing the INTERFACE file first,
       also write the implementation — into a file whose purpose says, verbatim, "The Store INTERFACE
       only — no implementation in this file"? That is the strongest prohibition available and it is
       ignored. `scope_rule` is emitted for it too (checked: `_siblings` comes from the PLAN, not
       from written files, so the first file of a package gets the rule).
    3. And there is a fix upstream of all of today's: the stripper should not delete a symbol THIS
       file's purpose promises and the sibling's purpose does not. That is the ownership rule the
       repair already uses, applied when the damage is done rather than after.
