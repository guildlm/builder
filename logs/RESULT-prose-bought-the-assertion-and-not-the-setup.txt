WHAT MOVED AND WHAT DID NOT
----------------------------
THE REPAIR WORKED — ON THE ASSERTION. The projects twins went from `assert 1` to `assert 2`.
That is precisely what the newly attached reason demanded ("assert EXACTLY 2"), and it is
the half that made chain4's projects witness unable to fail. Prose changed it.

THE REPAIR DID NOT TOUCH THE SETUP. The same reason says "POST THREE projects, NOT ONE" and
spends ten lines on why. The draw POSTed one, and two for the caps twin. Prose did not
change it.

AND THE CONTROL REGRESSED ON EXACTLY THE SAME AXIS. The tasks entry was NOT EDITED between
these two draws. It produced POSTs=3 on chain4 and POSTs=1 and 2 on v5. Same sentence, same
model, same flags — the setup count moved anyway, and moved to the same wrong values the
repaired projects arm landed on.

    Assertions are stable across draws and repairable by prose.
    Setup counts are neither.

The tasks regression is the decisive half, because it holds the spec text FIXED. Any story
in which the projects failure is about what the projects entry says has to explain why the
unedited tasks entry failed identically on the same axis in the same file-pair.


WHY THE MIRRORING MATTERS
--------------------------
In v5 the four twins are structurally IDENTICAL — same router arguments, same POST counts
(1 for defaults, 2 for caps), same assertion, and even the same compile defect: both caps
twins assign to an undeclared `w` after declaring `w1` and `w2`. projects_test.go reads as
router_test.go rewritten with /projects and models.Project substituted.

On chain4 they did NOT mirror: tasks POSTed 3 and asserted 2, projects POSTed 1 and asserted
1. So mirroring is not a constant of the generator — but when it happens, the second file
inherits the first file's setup, correct or not, and a per-test reason in the second entry
does not override what was inherited.

That is a testable claim and it predicts something specific: fixing the TASKS entry should
move the PROJECTS twins too, without touching the projects entry at all. Nothing has tested
that.

CORRECTION (same day, ~10:40) — "THE REPAIR WORKED ON THE ASSERTION" IS NOT IDENTIFIABLE
=========================================================================================
Checking the mirroring claim at N=2 undercut a conclusion stated above, and the conclusion
is withdrawn rather than defended.

taskapi-v5's empty-list twins are CHARACTER-FOR-CHARACTER IDENTICAL apart from the route,
the function name, and the string in t.Errorf:

    func TestListEmptyIsEmptyArray            func TestProjectListEmptyIsEmptyArray
        h := newRouter()                          h := newRouter()
        GET "/tasks"                              GET "/projects"
        want 200                                  want 200
        TrimSpace(body) != "[]"                   TrimSpace(body) != "[]"

Same structure, same helper, same assertion, same shape of error message. Those two are the
pair that FIRED FOR REAL against a genuine nil-slice defect — so mirroring reproduces a
CORRECT witness just as faithfully as it reproduced two broken ones in taskapipro. Mirroring
is quality-neutral: it copies whatever the first file did.

WHY THAT BREAKS THE CLAIM ABOVE
The section "THE REPAIR WORKED — ON THE ASSERTION" reads the projects twins going from
`assert 1` to `assert 2` as the repaired reason taking effect. Mirroring explains the same
observation with no reference to the repair at all: the projects file copied the tasks file,
and the tasks twins have asserted 2 in BOTH draws. The POST counts mirrored too — 1 and 2,
which no entry asked for — so the mechanism that demonstrably moved the setup numbers is
also sufficient for the assertion number. One mechanism, both columns.

    Two explanations, one draw, and nothing in this draw separates them. The repair's
    effect on the assertion is UNIDENTIFIABLE here.

WHAT STILL STANDS, AND WHY
The load-bearing observation does not depend on the projects arm at all: the TASKS twins
went POSTs=3 on chain4 to POSTs=1 and 2 on v5 with their entry UNEDITED. That is a single
artifact, a single unchanged sentence, and a setup count that moved anyway. "Setup counts
are not stable across draws and were not secured by prose" survives on that evidence alone.

What does NOT survive is the paired framing — assertions repairable, setups not — because
the assertion half rested on the projects arm, and the projects arm is a copy.

THE HEADLINE SHOULD HAVE BEEN NARROWER
The honest one-line result of this draw is:

    The tasks paging witnesses regressed with their spec entry unchanged, and the projects
    file mirrored them, so this draw contains ONE independent observation, not two.

The prediction grades are unaffected — POSTs THREE was predicted and one was drawn, sites
flipping to CAUGHT was predicted and cannot happen. Both still WRONG.

THE DISCRIMINATING EXPERIMENT, NOW SPECIFIED
Mirroring and per-entry prose make the same prediction whenever the two entries agree. They
diverge only when the entries DISAGREE — chain4 is the existing instance, where the entries
differed (tasks had a reason, projects did not) and the files did NOT mirror. So:

    Draw taskapipro with the TASKS entry deliberately asking for a different item count
    than the PROJECTS entry. If the projects file follows its own entry, prose wins. If it
    follows tasks, mirroring wins. One draw, binary, and it settles which mechanism the
    campaign has actually been measuring all week.

That is worth more than any further repair to the projects wording, and it must wait for
the draws to drain — see NOTE-do-not-touch-src-until-the-draws-drain.txt for the adjacent
rule about the generator.


QUANTIFIED BY INSTRUMENT (_twin_witness.py), AND THE INSTRUMENT WAS VALIDATED FIRST
===================================================================================
Hand-reading four test bodies is how everything above was established. _twin_witness.py
counts the same three numbers mechanically — the page size the router is built with, the
items the test seeds, and the length it asserts — and applies the only relation that makes
a paging test a witness:

    seeds < bound   CANNOT-PASS     fails against a correct handler
    seeds == bound  CANNOT-FAIL     a handler ignoring the page size returns the same count
    seeds > bound   DISCRIMINATES   the only case worth writing

VALIDATED AGAINST GROUND TRUTH BEFORE USE. Run on chain4, whose four twins were graded by
mutation days ago, it reproduces those grades exactly:

    chain4  DISCRIMINATES  TestListDefaults...        seeds=3 asserts=2     (graded CAUGHT)
            DISCRIMINATES  TestListCapsAt...          seeds=3 asserts=2     (graded CAUGHT)
            CANNOT-FAIL    TestProjectListDefaults... seeds=1 asserts=1     (graded SURVIVED)
            CANNOT-FAIL    TestProjectListCapsAt...   seeds=1 asserts=1     (graded SURVIVED)
            -> 2 of 4 witnesses can discriminate

Four for four against independent mutation verdicts. A static count agreeing with a dynamic
grade on every row is what earns it the right to be read on a tree nobody has graded.
