PREDICTION — jsonapi's invalid-JSON 400, and a test of my own conclusion
========================================================================
2026-07-25, before the edit. Fourth closure attempt.

THE HOLE
  The spec promises "400 for invalid JSON OR an empty message" — two conditions. The suite
  pins the empty-message one ("empty message status = %d, want 400"). Break the
  invalid-JSON 400 and everything stays green. Identical in shape to shortener's
  malformed-JSON hole, which this method already closed.

WHY THIS SPEC — it tests the constraint I just wrote down
  The tasks-api grading concluded: "the method's real constraint is not the edit but the
  coder — closing a hole needs a GREEN regeneration, and green is what the coder cannot
  reliably deliver on the bigger specs." Both successes were on shortener (7 files); both
  failures were on 14- and 8-file specs. jsonapi is FOUR files. If size is the constraint,
  this should close. If it fails anyway, size was the wrong variable and I should say so.

THE EDIT
  A named test, with the trap spelled out — `{}` is valid JSON and takes the OTHER branch,
  the same distinction that mattered on shortener:

      TestInvalidJSON: POST /echo with a body that is NOT valid JSON — send the raw bytes
      `{"message":` (truncated ON PURPOSE; do NOT send `{}` or `{"message":""}`, which are
      valid JSON and take the empty-message branch that is already covered) -> 400.

PREDICTION
  1. TestInvalidJSON is written and passes.
  2. The build greens. This is the real claim: four files, a spec the base has greened
     before, and the recipe has landed twice.
  3. The mutation flips SURVIVED -> CAUGHT, graded against the unedited artifact's
     SURVIVED as control.
  4. jsonapi's registered mutations (echo Content-Type, 405 method guard) stay CAUGHT.

  If (2) fails on a four-file spec, "the coder cannot green the bigger specs" is not the
  right description of the constraint, and the honest correction is that regeneration is
  simply unreliable at any size — which would make every future closure a coin flip rather
  than a procedure.

===========================================================================
GRADED — all four held, and the constraint I put on trial is CONFIRMED.

  RUN: 3-member fleet, 57 seconds, 2 fix rounds, ZERO escalations, rc=0.

    1. TestInvalidJSON written                                      YES
    2. Build greens                                           3/3 GREEN
    3. The invalid-JSON 400, graded per SITE against the unedited artifact:

           BEFORE   line 28  SURVIVED   http.Error(w, "invalid json", 400)
                    line 32  CAUGHT     http.Error(w, "message required", 400)
           AFTER    line 32  CAUGHT     w.WriteHeader(400)
                    line 37  CAUGHT     w.WriteHeader(400)

       Both sites now defended. The half-defended promise is whole.
    4. Registered mutations: Content-Type CAUGHT, 405 guard NOAPPLY (the regenerated code
       expresses the method guard differently, so that mutation no longer applies — not a
       regression, an artifact of regeneration).

  THE CONSTRAINT: CONFIRMED, and sharply. This spec is FOUR files and greened in 57
  seconds with ZERO escalations. tasks-api is eight and burned 3100 seconds, nine rounds
  and nine escalations without greening. taskflow is fourteen and failed twice.

      spec        files   result                       time
      jsonapi        4    GREEN, hole closed             57s
      shortener      7    GREEN, two holes closed    891/1351s
      tasks-api      8    RED, ungradeable             3100s
      taskflow      14    RED, ungradeable      2817s (+ earlier)

  So "the coder cannot green the bigger specs" survives its test rather than being
  corrected. Closing a hole is a procedure on small specs and a coin flip on large ones —
  and the boundary in this corpus sits somewhere between seven files and eight.

  A GRADING BUG FOUND ON THE WAY, worth more than the closure. The uniqueness guard added
  to _hole_hunt this afternoon — refuse if the line text is not unique — blocked this
  grading outright: the regenerated code writes `w.WriteHeader(http.StatusBadRequest)`
  TWICE, byte-identical, so neither site could be addressed by text. Grading by LINE INDEX
  fixed it. The guard was the right call for a mutator that cannot see which line the
  detector chose; the real fix is for the mutator to carry the index, and this is the first
  case where text alone genuinely cannot distinguish two sites.
