  Six failures, ONE cause. The store hands the first task ID 0; every test then asks for
  id 1 and gets 404. The last row is the one that says it outright, and it is the only one
  that does — the other five present as routing or lookup bugs.

THE SPEC SILENCE
      "...a map[int]Task and an auto-incrementing nextID."

  It never says where nextID STARTS. A Go int field zero-values to 0, so the first task
  gets ID 0, while every generated test assumes 1 — which is what auto-increment means
  everywhere else, and the model is right to assume it.

AND IT IS NOT MERELY A DISAGREEMENT — IT IS A LATENT BUG
      func (s *MemStore) Update(t Task) error {
          if t.ID == 0 { return ErrNotFound }

  The code uses 0 as the "unset ID" sentinel, which is idiomatic and correct on its own.
  Combined with a sequence that STARTS at 0, the first task ever created is permanently
  unupdatable. Both halves are defensible; the spec never made them agree. That is a defect
  that ships green in any suite whose tests happen to start from the second record.

THE EDIT — say where it starts, and say why
  NewMemStore sets nextID to 1, with the reason inline: 0 is both the zero value and the
  sentinel Update uses for "no ID", so a task with ID 0 can never be addressed.

BUT "GREEN" HERE IS NOT REPRODUCIBLE, AND THAT IS THE REAL RESULT
  The builder returned rc=0. Running the suite again afterwards:

      full suite, 12 runs:  PASS=9  FAIL=3

      --- FAIL: TestList200
          expected tasks S and S, got task2 and task1

  MemStore.List iterates the map directly and does not sort. The spec requires it —
  "List returns a copy sorted by ID" — so this is a plain implementation defect against an
  explicit requirement, and it survived because ONE test run cannot tell a correct sort
  from a lucky map iteration. Go randomises map order per run; with two items a wrong
  implementation passes about as often as it fails.

  So the builder's green verdict is a SAMPLE, not a proof, wherever the code has
  order-nondeterminism. It reported success on the run that happened to come out sorted.
  Note the test passes 6 out of 6 when run ALONE and fails 3 in 12 with the full suite —
  the flake rate itself depends on what else ran, which is why a single -run probe would
  have "cleared" it.

  This is the same shape as everything else measured today, now in the production path:
  a numerator with no denominator. "tests passed" needs "on how many runs".
