THE LAW THAT COVERS ALL FOUR
-----------------------------
    A test is written from ITS OWN description. Text elsewhere — a sibling entry, the
    implementation file's entry, a cross-reference, three sentences up — does not reach
    it. And WITHIN that description, a concrete value outranks an instruction about what
    not to do.

Every result this week is an instance:

  taskapi healthz     prohibition alone in the test's description        -> HELD
  shortener stats     prohibition + the value, same description         -> value won
  taskapipro tasks    reason in the test's own description              -> CAUGHT
  taskapipro projects reason only via cross-reference to the twin       -> SURVIVED x3

The last two are the sharpest, because they are in the SAME ENTRY three sentences apart:
the clamp test carried its own reason and was CAUGHT while the paging test carried only an
instruction and SURVIVED. So the unit is not the entry and not the file — it is the
individual test's description. The note from the 28th said "proximity does not carry"; this
is the same law from the other side, and it explains a prohibition and a justification with
one rule instead of two.

THE PRACTICAL CONSEQUENCES, IN ORDER OF USEFULNESS
---------------------------------------------------
1. NEVER STATE THE CORRECT VALUE IN A SENTENCE THAT FORBIDS ASSERTING IT. The sentence is
   read for the value. If a step must not be asserted, say so and say nothing else about
   what it returns — taskapi proves the bare prohibition works.
2. A REASON MUST BE REPEATED PER TEST. It is a per-test cost, payable at every test, and
   cross-referencing the twin does not discharge it. Verbose, and cheaper than a SURVIVED.
3. THE VALUE MAY LIVE ELSEWHERE SAFELY. taskapi documents the healthz body in the
   implementation entry and the test still did not assert it, so a spec does not have to
   choose between documenting behaviour and forbidding an assertion — it has to keep them
   in different entries.

WHAT THIS DOES NOT EXPLAIN
---------------------------
PRESENCE. taskflow's projects-sorted test has a reason in its own description and is still
not written — the law above governs what a test that gets written CONTAINS, not whether it
appears. See FINDING-presence-and-discrimination-are-different-failures.txt; the
name-collision account there is the candidate for the other half, and its retest is queued.

⚠️ BOUND: four instances, one model, one night. The shortener/taskapi pair is a clean
controlled contrast; the taskapipro pair is cleaner still, being same-entry. But three of
the four are HTTP handler suites in the same corpus and none is a replication at N>1 of the
same sentence. The rule earns its confidence from covering four independent outcomes with
one mechanism, not from repetition — and taskapipro-v5, landing within the hour, is the
first genuine retest of consequence 2.
