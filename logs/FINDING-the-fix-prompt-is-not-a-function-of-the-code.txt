FINDING — the fix prompt carries a wall-clock timestamp, so it is not a function of the code
=============================================================================================
31 July. Third consumer of toolchain output found to share one blind spot, and the only one of the
three that CAUSES divergence rather than failing to detect it.

`_canonical_toolchain_output` EXISTS TO PREVENT EXACTLY THIS, AND SAYS SO
    "Strip the run-to-run noise out of go's output BEFORE it reaches the model. The fix prompt embeds
    toolchain output verbatim, and that output carries text that changes between runs of identical
    code: per-package durations, per-test durations, and — worst — `(cached)`."

    It does that correctly:
        --- FAIL: TestCreate (0.01s)     ->  --- FAIL: TestCreate
        ok  guildlm.dev/.../money 0.310s ->  ok  guildlm.dev/.../money

    And leaves this untouched:
        2026/07/31 14:40:37 POST /accounts -> 201 (8µs)   ->   unchanged

    A spec whose tests serve requests therefore sends the model a DIFFERENT PROMPT on every fix
    round for identical code. The docstring's own standard — "a prompt should be a function of the
    code" — is violated in the function written to enforce it.

THIS IS THE MECHANISM BEHIND THE DIVERGENCE OBSERVED TODAY
    arm-1 and arm-2: same spec, same flags, same server process, BYTE-IDENTICAL source trees, and
    different error surfaces at fix round 1. Generation was identical; the first thing that differed
    was the first prompt built from toolchain output.

⚠️ CORRECTED — "THE FIX LOOP ITSELF DIVERGES" IS WRONG. ONLY THE HASH DOES.
    I wrote that the varying prompt makes the fix loop diverge, and then measured both arms end to
    end:

        fix targets, in order   IDENTICAL (arm-2's sequence is a prefix of arm-1's, no differing
                                index in the common length)
        final .go files         18 of 18 BYTE-IDENTICAL, none present in only one tree

    So the timestamped prompt did NOT change what the model fixed or what it wrote. The two runs
    differ in exactly one observable: the error-surface HASH, which is computed from the same
    unnormalised text.

    THE CORRECTED CLAIM: the prompt is not a function of the code — that part stands, and it is a
    real defect because nothing guarantees the model ignores the varying tokens. But on these two
    runs it evidently did ignore them, and the only measured consequence is the defeated repeat
    detector.

    ⚠️ I inferred "the fix loop diverges" from a divergence at line 39 of a log, without checking
    whether anything downstream of that line differed. The hash line WAS the divergence. Sixth time
    today that a real mechanism got attached to a consequence the evidence did not show.

    Three consumers, one blind spot:
        _error_signature          fails to DETECT a repeat        -> extension rounds run to the cap
        _error_keys (mine, today) fails to compare error sets     -> false refusals in the repair gate
        _canonical_toolchain_output  feeds the MODEL varying text -> the fix loop itself diverges

⚠️ WHAT THIS DOES **NOT** EXPLAIN, AND THE DOCSTRING ASKS ABOUT
    The same docstring ends: "generation is deterministic (measured: three 1200-token completions at
    temp=0.1, byte-identical) and yet same-arm runs generate DIFFERENT files. Something upstream of
    the fix loop varies per process. Look there, not here." That question is still open.

    GENERATION HAPPENS BEFORE ANY TOOLCHAIN OUTPUT EXISTS. This finding cannot touch it. What it
    explains is fix-loop divergence within a process; what remains unexplained is generation
    divergence across processes, which is what that note was about. Adjacent, not the same, and the
    temptation to file this as "the 18 July question, answered" is exactly the scope error this
    session has corrected five times.

FIX, queued behind the freeze with the same normalisation as the other two consumers
    Add the timestamp and unit-duration patterns to `_canonical_toolchain_output`. Reject condition:
    the fix prompt must still distinguish two genuinely different failures, or the loop loses the
    signal it fixes on.

EXACT BOUND ON THE OBSERVABLE CONSEQUENCE — every differing line, categorised
    220 comparable lines · 38 differ (17%)

        28   app-log lines carrying a wall-clock timestamp   <- the noise itself
         8   error surface hashes                            <- the consequence
         2   "deterministic fix in <file>" lines, SWAPPED    <- see below

    And 18 of 18 .go files byte-identical. So the timestamp noise is fully accounted for: it prints
    itself 28 times, it corrupts 8 hashes, and it changes nothing else in the output.

THE TWO LEFTOVER LINES ARE A GENUINE, HARMLESS ORDER SWAP
        line 49  arm-1: deterministic fix in internal/store/memory_test.go
                 arm-2: deterministic fix in internal/service/service_test.go
        line 50  arm-1: deterministic fix in internal/service/service_test.go
                 arm-2: deterministic fix in internal/store/memory_test.go

    The same two deterministic fixes, applied in the opposite order. Both runs produce identical
    files, so the swap costs nothing here — but it is a real ordering nondeterminism in a pass whose
    name says "deterministic", and it is worth knowing that the pass's file iteration is not stable.

    ⚠️ NOT CHASED. It has no measured consequence, the queue has four items with evidence behind
    them, and "the deterministic pass is not order-stable" is the kind of finding that reads as
    alarming and costs a day to establish is harmless. Recorded so the next person who sees an order
    swap in a diff knows it has been seen and is not new.

THE THREE ARMS' FIX-LOOP WORKLOADS ARE IDENTICAL, AND THEIR WALL TIMES ARE NOT
    arm-1  model fixes 58 · deterministic 7 · kept 58 · fell back 0    77.0 min
    arm-2  model fixes 58 · deterministic 7 · kept 58 · fell back 0    82.2 min
    arm-3  model fixes 55 · deterministic 7 · kept 54 · fell back 0    93+ min, still running

    arm-1 and arm-2 did exactly the same work — same counts in every column — and differed by 5.2
    minutes. arm-3 is at 55 of the same 58 and has already run 11 minutes longer than arm-2's total.

    So the fix loop's WORK is deterministic and its DURATION is not. That is unsurprising for an
    inference server under varying load, and it is worth recording only because it bounds what a
    duration can be used for: NOTHING comparative. Today's "~6.7 min per fix round" and "arms are 72%
    of wall clock" are averages over a quantity that varies by 20% between byte-identical runs.

    ⚠️ WHICH SLIGHTLY WEAKENS THE COST ARGUMENT FOR THE QUEUED FIX. "~20 minutes saved per affected
    build" was derived from arm-1's marginal minutes; on arm-3's pace the same three extension rounds
    would cost more, on arm-2's less. The ROUND COUNT saved (3 of 8) is the stable number; the
    minutes attached to it are not, and the finding should be read as "three rounds" first and
    "twenty minutes" second.
