THE TENSION THIS CREATES, which I cannot resolve and will not paper over
    archived A arms, OLD harness, clause PRESENT   ->  CONSOLIDATED 3/3
    fresh controls, NEW harness, clause PRESENT    ->  SPLIT        2/2
    fresh arms,     NEW harness, clause WITHHELD   ->  CONSOLIDATED 2/2

    The clause alone does not determine the outcome: with it present, the old harness consolidated
    and the new one splits. So today's harness changes ALSO matter, and the clause appears to be
    necessary-but-not-sufficient for the correct split under the current code.

    I do not have a mechanism for the first row versus the second. The changes I made today act on
    memory.go, which is generated SECOND, and cannot alter what store.go writes first. That gap was
    already recorded when control-1 came in, and this result does not close it.

    strength of the finding that motivated it, I would have reintroduced the stub on the spec this
    campaign draws most. The pre-registration's value was not the prediction — that was wrong — it
    was fixing the endpoint and the reject conditions before the table existed.

WHAT THE CLAUSE ACTUALLY CHANGES IN THE OUTPUT — broader than MemStore
════════════════════════════════════════════════════════════════════════════════════════════
    spec gives store.go:  "The Store INTERFACE only — no implementation in this file."

    control store.go declares:  Store
    arm     store.go declares:  ErrNotFound, ErrExists, Store, MemStore, NewMemStore,
                                and all six MemStore methods

With the clause present the file is the interface and nothing else — 413 bytes, two imports, one doc
comment. With it withheld the model wrote a COMPLETE, SELF-SUFFICIENT store package in one file:
sentinels, interface, implementation, and the imports to support them (errors, sort, sync).

    ⚠️ THE OVER-REACH IS NOT NARROWLY ABOUT MemStore. It includes ErrNotFound and ErrExists, which
    ledger's spec does not assign to store.go at all. So the clause is not "the sentence that stops
    the implementation moving"; it is closer to the sentence that keeps store.go a DECLARATION-ONLY
    file. Stating the distinction because "it prevents consolidation" invites a mechanism about
    MemStore specifically, and the evidence is wider than that.

    A HYPOTHESIS, AND ONLY THAT: the clause names "the interface AND its implementation" as two
    things, which may cue that the implementation is a separate artifact living elsewhere. Withhold
    it and the model defaults to writing a package that works on its own. Nothing here tests that,
    and one prompt sentence has now surprised me once already today.

⚠️ AND IT EXPOSES A LIMIT IN MY OWN GRADER. `_parity_ab.sh` decides SPLIT vs CONSOLIDATED by asking
whether store.go declares MemStore. A store.go that took the SENTINELS but not MemStore would grade
SPLIT while still violating "the interface only". The grader was validated against known-labelled
trees and it discriminates the cases it was built for — but it measures one symbol, and this result
shows the failure mode is wider than one symbol.
