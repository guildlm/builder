RESULT — how many of the capstone's flips are attributable to the REDRAW at all
================================================================================

16:54 on 29 July. Two claims were retracted in the previous hour for the same reason: a
quantity read off a tree that the fix loop had rewritten, compared against one it had not.
That failure is not specific to those two claims. The capstone compares 140 live-in-both rows
across v4 and v5 trees, and NOTHING in that comparison knew how much repair either side had
absorbed. This measures it for every artifact at once.

    A sweep's verdict ABOUT AN ARTIFACT is unaffected — the shipped tree is the deliverable
    and how it got there does not matter. What is affected is reading a v4-vs-v5 DIFFERENCE
    as a fact about the SPEC, which is exactly what the campaign's headline does.

WHAT SPOILS PROVENANCE, and what does not
    `fixing <file>`                   a MODEL rewrite — assertions, seeding, names. SPOILS.
    `deterministic fix in <file>`     goimports-class. Does not touch assertions. Does not spoil.
    `rebuilt a request ... (drained)`  replaces a request; counted separately because it
                                      changes how many items land without moving an assertion.

    8  MISMATCHED      one side model-rewritten, the other not. THE RETRACTED SHAPE.

THE ONE THAT CANNOT, AND IT IS THE WORST-LOOKING CASE
usersapi's v5 draw took exactly one model rewrite, and it was of a TEST FILE:

    compile/test FAILED, fix round 1/5
      fixing users_test.go
    converged to green after fix round 1

That draw's only capstone flip is a DEFENCE GAINED — middleware.go `boundary >= -> >`, SURVIVED
in v4 and CAUGHT in v5. A model rewriting a test file and a previously-undefended site becoming
defended in the same draw is precisely the confound, and the two cannot be separated from
outside. The row is not evidence that a redraw gained a defence; it is equally evidence that
the fix loop wrote a better test.

⚠️ 11 OF THE v4 BASELINE TREES HAVE A SINGLE-SECOND MTIME, AND THEIR DRAW CANNOT BE DATED
Every .go file in them shares one identical timestamp to the second — demo-small, jsonapi,
logstats, numkit, ratelimit, taskflow, tasks-api, usersapi, workapi, workerpool, plantedred.
A draw writes files seconds apart; every genuinely-drawn tree here has a spread of 43-879s.
And FOUR DIFFERENT SPECS — demo-small, logstats, numkit, workerpool — share the exact same
second, 07-27 02:01:08, which no set of four independent generations produces.

    MEASURED: one operation wrote each of those trees, and one operation wrote four of them
    together. No ab-run log sits anywhere near those times, so time cannot identify their
    draw, and that is the operational consequence.

    NOT MEASURED, and an earlier version of this file asserted it: WHAT that operation was.
    Nothing in this repo copies into generated/<spec>-v4 — every `cp -r` found goes the other
    way, out of a v4 tree into a `_`-prefixed keep directory. So the write came from outside
    the repo's scripts or from one no longer present, and "restored wholesale" was an
    inference stated as a finding. The distinction matters because the mechanism is what
    would say whether the CONTENT is still the drawn content.

    Either way the v4 half of the baseline is partly unauditable, and stays that way unless a
    draw records its own provenance into the tree — which is what <out>/.pre-fix.json would
    do. NOT DONE TODAY: src/ is holding still while a control draw runs.

⚠️ WHAT THIS DOES NOT SAY. It does not retract the capstone. Six-up-and-two-down remains the
best available estimate of redraw drift and the argument for it is unchanged. It says the
estimate rests on eight rows of which two are fully controlled, and that a future campaign
wanting a defensible drift figure must match provenance BEFORE comparing, not discover it
afterwards. The instrument now exists: _provenance_census.py, and _twin_witness --log=.

METHOD NOTES, because two matcher bugs were found and fixed while building this
  * Keying on the newest FILE dated taskapipro-v4 and ledger-v4 a week after their draws —
    their go.mod alone was rewritten 07-26 15:19 by a later corpus fix. Keying on the newest
    .go file matches both exactly. That bug silently lost the campaign's namesake artifact.
  * A zero mtime spread means COPIED, not drawn, and the tool now says RESTORED rather than
    picking whichever log sits nearest a copy operation. Before that it reported 12 artifacts
    UNKNOWN, which was the symptom that led here.
  * One-sided evidence is still evidence: if the v5 tree was model-rewritten, the difference
    is unattributable whatever the v4 log says. Reporting those as UNKNOWN threw away four
    verdicts the evidence supported.

=====================================================================================
The flips were split by provenance above. The 140 live-in-both rows they are drawn from
split as well, and that is the number that says how well-founded the drift estimate is:

    PARTIAL        87 live rows   62%    v5 clean, v4 tree undatable
    MISMATCHED     28 live rows   20%    one side model-rewritten

Two artifacts, taskflow and tasks-api, carry 73 of the 140 rows — just over half — and both
are PARTIAL for the same reason: their v5 draws converged on deterministic fixes alone (clean),
while their v4 trees have a single-second mtime and cannot be matched to a build log.

    So the dominant uncertainty in the capstone is NOT model rewrites. It is that half the
    baseline's v4 side cannot be dated. That is a different problem with a different fix, and
    `.pre-fix.json` addresses it going forward while doing nothing for the rows already taken.

THE WORRY THIS ANSWERS: does provenance mismatch INFLATE the flip count?
If a model rewriting a test file were manufacturing flips, the MISMATCHED bucket would show
the highest flip rate. It shows the lowest:

    CLEAN-BOTH     2 flips / 25 rows    8.0%
    PARTIAL        5 flips / 87 rows    5.7%
    MISMATCHED     1 flip  / 28 rows    3.6%

⚠️ AND THE COUNTS ARE FAR TOO SMALL TO SEPARATE. 2, 5 and 1. Any two of these rates are
indistinguishable at this size and the ordering would move if a single row changed verdict.
What it rules out is a LARGE inflation effect — dirty rows are not flipping several times more
often than clean ones — and that is the whole claim. It does not license reading the dirty
rows as evidence about closures; the usersapi row is still the one where a test file was
rewritten in the same draw that gained a defence, and that stays unattributable whatever the
bucket rate says.


PER-ROW PROVENANCE (17:56) — the artifact-level verdict was too coarse, and it was pessimistic
================================================================================================
The census grades an ARTIFACT clean when no model rewrite touched it anywhere. For a specific
ROW that is the wrong question: what can move a mutation verdict on middleware.go is a rewrite
of middleware.go, not a rewrite of some other file in the tree.

AND ONE MORE v4 LOG WAS RECOVERED, by file set rather than by time.
Time failed for 11 v4 trees. A build log lists every file it generated, so the FILE SET
identifies the spec generation that produced a tree. Tried on all seven PARTIAL artifacts; it
disambiguates exactly one, and it happens to be the one that matters most:

    taskflow-v4   15 files.  19 candidate logs, and ONLY ab-taskflow-v4-07261523.log
                  generated 15 — the others produced 12, 13 or 14. Unique on count alone.
                  That log converged to green after fix round 1 and the tree is green today.

    ⚠️ STRONG CANDIDATE, NOT PROOF. taskflow-v4's bytes carry a single-second mtime of
    07-27 00:15:07, nine hours after that log closed, and what performed that write is still
    unidentified. The file set says which SPEC VERSION the tree came from; it cannot prove
    which RUN wrote those bytes. Recorded as a candidate and used as one.
    The other six PARTIAL artifacts gain nothing: their file sets are identical across every
    draw, so the technique identifies nothing at all for them.

WHAT THAT LOG SAYS, and it is the interesting part
taskflow-v4 took exactly ONE model rewrite, of `router.go`, prompted by a pointer-to-interface
type error in main.go. Under the artifact-level rule that makes taskflow MISMATCHED — worse
than the PARTIAL it was. But taskflow's four flipped rows are in middleware.go, pagination.go,
tasks_handler.go and store.go. NONE of them is router.go.

⚠️ FILE-LEVEL IS BETTER THAN ARTIFACT-LEVEL AND STILL NOT AIRTIGHT. A rewrite of router.go can
change what a test of tasks_handler.go observes, because the router wires the handlers together
— so "clean for this file" bounds the risk, it does not eliminate it. The honest ordering is:
no rewrites anywhere (shortener, 2 rows) > no rewrite of this file (taskflow, 4 rows) >
unmatched (2 rows).

⚠️ AND usersapi IS NOT RESCUED BY THIS. Its v5 draw's single rewrite was users_test.go, and its
flip is middleware.go going from SURVIVED to CAUGHT. A rewritten TEST is exactly what could
newly catch a middleware mutation — the file-level rule says "clean for middleware.go" and
that is the wrong file to be asking about. It stays the one flip that cannot be attributed,
and this refinement does not change that.
