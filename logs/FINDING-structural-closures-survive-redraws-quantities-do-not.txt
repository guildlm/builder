FINDING — a closure that changes a SIGNATURE is durable; one that changes a QUANTITY is not
============================================================================================

Measured 29 July ~10:14 on taskapipro-v5, mid-fix-loop. Two closures made days apart on the
SAME spec, redrawn in the SAME run, with opposite outcomes — which is the cleanest control
this campaign has produced, because everything except the shape of the closure is held
fixed.

THE TWO RESULTS, SAME ARTIFACT, SAME DRAW

    config wiring       _dead_config: 0 of 6 fields dead      SURVIVED THE REDRAW
      draw4 landed NewRouter(..., defaultPageSize, maxPageSize int), both handlers holding
      and reading the fields, main() passing cfg.*. taskapipro-v5 reproduces it: 0 dead,
      same as draw4, and projects.go reads h.defaultPageSize at three sites.

    paging witnesses    _twin_witness: 0 of 4 discriminate    DID NOT SURVIVE
      chain4 had 2 of 4. The seed counts went 3,3 -> 1,2 on the arm whose entry was not
      even edited.

THE DISTINCTION
The config closure changes STRUCTURE: a function signature, two struct fields, and the call
sites that must agree with them. The paging closure changes a QUANTITY: how many items a
test body seeds before it asserts.

    Structure is held in place by everything that touches it. A signature has call sites,
    a field has readers, a test function has a name the spec checks. A quantity inside a
    test body is held in place by nothing at all — no compiler, no caller, no other line
    in the file has an opinion about whether the loop runs once or three times.

That is why prose was enough for one and not the other. The spec's paragraphs did not make
the signature survive; the compiler did. Remove the argument and nothing builds. Change 3 to
1 and everything builds, the suite goes green, and the only witness that would object is the
one being weakened.

IT ORGANISES THE WHOLE CAMPAIGN'S RESULTS

    closure                        shape        redrawn as        verdict
    -----------------------------  -----------  ----------------  ---------
    taskapipro config wiring       structure    0/6 dead          held
    taskapi empty-list x2          structure    raw-body assert   held (fired for real)
    usersapi empty-list            structure    raw-body assert   held
    shortener race Lock->RLock     structure    CAUGHT            held
    workapi Delete-404             structure    (queued)          —
    taskapipro paging x4           QUANTITY     0/4 discriminate  LOST

Every closure that survived is the presence or absence of a thing — an assertion, a lock
type, a field, a signature. The only one that failed is the one that is a NUMBER. And the
presence census agrees from the other side: 0 of 174 spec-named tests missing across 20
trees, so "does this thing exist" is close to solved while "is this number right" is not.

WHAT IT PREDICTS, AND THIS IS FALSIFIABLE
  * workapi's Delete-404 is structural — an assertion that exists or does not. PREDICT it
    holds. (Already registered at 85% in the prediction file, for a different reason; this
    gives that number a mechanism rather than a base rate.)
  * Any future closure phrased as a count, a bound, a page size, a retry limit or a timeout
    is in the fragile class and should be gated, not written into prose. The gate design is
    in NOTE-the-paging-seed-gate-has-a-precedent-and-a-trap.txt.
  * A quantity CAN be made structural, and that is the cheaper fix than a gate where it
    works: a named constant the test must reference, or a seeding helper `seedN(h, 3)`
    declared in the spec, converts "how many" into "does this call exist" — which is the
    class that survives. Untested, and the obvious first experiment after the draws drain.

⚠️ BOUNDS
Six closures, one corpus, one model, and the two arms of the decisive comparison are in one
artifact. The config/paging contrast is strong precisely because it is same-spec same-draw,
and that is also its limit: taskapipro may be unrepresentative. The empty-list and race rows
are supporting evidence from other artifacts, not replications of the contrast itself.

⚠️ AND THE TREE HAS NOT FINISHED. _dead_config was run on a complete tree (main.go landed)
but the fix loop is still editing test files. Config fields and their readers are not what
the loop is touching, so the 0-of-6 is stable; if a later round rewrites main.go this must
be re-read.


ADDENDUM (10:35) — MIRRORING IS THE MECHANISM, AND STRUCTURE IS WHAT MAKES IT VISIBLE
======================================================================================
Round 3 of the taskapipro-v5 fix loop produced a compile error that turns this law from a
correlation into a mechanism, by showing the same copying behaviour where the compiler CAN
object.

    internal/api/projects.go:71:55: too many arguments in call to h.svc.List
        have (context.Context, int, int, string)
        want (context.Context, int, int)

The two services genuinely differ — tasks filters by status, projects does not:

    TaskService.List(ctx, limit, offset int, status string)
    ProjectService.List(ctx, limit, offset int)

and tasks.go line 71 is:      h.svc.List(r.Context(), limit, offset, status)
and projects.go line 71 is:   h.svc.List(r.Context(), limit, offset, status)

The same call, at the SAME LINE NUMBER, in both files. The fix loop made projects.go mirror
tasks.go line for line, carrying across a parameter the projects service does not have.

MIRRORING IS NOT A GENERATION ARTEFACT. It was already measured in generation — taskapi's
empty-list twins character-identical, taskapipro's four paging twins identical including
their seed counts and their undeclared-w defect. Here it is again in REPAIR, a different
phase with a different prompt and a different objective. The pipeline copies the sibling
file at every stage that writes one.

AND THAT IS WHY THE STRUCTURAL/QUANTITY SPLIT HOLDS

    mirrored thing        who objects        outcome
    --------------------  -----------------  -------------------------------------------
    a SIGNATURE           the compiler       loud, caught in the same round, repaired
    an ASSERTION          the compiler/test  loud if it does not compile or does not pass
    a SEED COUNT          nobody             silent, shipped, 0 of 4 witnesses

Same mechanism, three visibilities. The law is not that quantities are copied more carelessly
than structure — they are copied the SAME WAY, by the same mirroring. The difference is
entirely in whether anything downstream is in a position to complain. A mirrored signature
gets one compile error and one fix round. A mirrored seed count gets a green suite.

    Mirroring is the cause. Structure is not protection against it — structure is what
    makes its failures announce themselves.

This is a better statement of the law than the one at the top of this file, and it was
available only because the fix loop happened to mirror something the compiler could see.

⚠️ IT ALSO MEANS THE FIX LOOP CAN INTRODUCE DEFECTS WHILE WIDENED. Round 3's error did not
exist in the as-drawn tree; projects.go called List with three arguments and compiled. A
widened round wrote a fourth. The measured sites survived it — all four paging sites and
all six config fields are still present and still wired, checked after the rewrite — but
that is luck this time, not a guarantee, and it is the second round in a row where the
check was necessary rather than ceremonial.


A POSITIVE INSTANCE (11:10) — A SPEC PREEMPTING AN UNREACHABLE STATE, AND IT WORKED
===================================================================================
Found while checking workapi's auth token for the Delete-404 verification. Not sought.

specs/workapi.yaml warns about mode 3 — the failure that is invisible to every runtime
instrument, because the line the test targets cannot be reached at all:

    "TestValidateEmptyAuthToken — build a Config VALUE DIRECTLY with a field-named literal
     ... Do NOT call Load() here, and do NOT try to reach this state by setting AUTH_TOKEN
     to "": Load treats an EMPTY env var as UNSET and substitutes the default "secret", so
     an empty AuthToken is UNREACHABLE through Load by construction — the token would come
     back "secret", Validate would correctly return nil, and the test would FAIL AGAINST A
     CORRECT IMPLEMENTATION."

workapi-v5 wrote it exactly as instructed:

    func TestValidateEmptyAuthToken(t *testing.T) {
        ... AuthToken: "",        // a Config value built directly
        ...                       // Validate() called on the value, Load() never touched

THE ENTRY IS THE SAME SHAPE AS THE FAILED PAGING ONE — long, reasoned, naming the wrong
approach and explaining precisely why it fails. Here it worked. The difference is what it
was asking for: a CONSTRUCTOR CHOICE (build the value directly, do not call Load), which is
structural — the test either calls Load or it does not, and which it calls is visible in the
source and load-bearing for whether the test compiles into the shape asked for.

    Reason bought the structural choice here, exactly as it bought the router arguments in
    taskapipro and failed to buy the seed count. Three instances now, same direction.

AND IT IS THE RIGHT WAY TO HANDLE MODE 3. The alternative repairs are worse: making the
state reachable would mean weakening Load's empty-means-unset behaviour, which is correct;
dropping the test would leave Validate's contract undefended. Testing the contract at the
level the contract is about — a Config value, not an environment — keeps both. The spec says
so in one sentence: "Validate's contract is about a Config value; test it on a Config value."

⚠️ NOT A CLOSURE, AND NOT COUNTED AS ONE. Nothing was mutated here and no grade was taken.
This is a spec instruction being followed, observed in passing, which is weaker evidence
than a mutation verdict and is recorded as such.


SHARPENING (11:15) — IT IS NOT THE COMPILER, AND THE BETTER WORD IS PRESENCE
============================================================================
"Structural closures survive" invites a trivial reading: they survive because the compiler
enforces them. Tested it, and that reading is wrong.

The empty-list closures are structural and NOTHING enforces them:

    usersapi-v5    if strings.TrimSpace(w.Body.String()) != "[]" {
    tasks-api-v5   if strings.TrimSpace(rec.Body.String()) != "[]" {

Both present, both graded (usersapi CAUGHT by mutation, taskapi's pair fired against a real
defect). Delete that line and the test still compiles and still passes — it is simply
weaker. No compiler, no caller, no signature holds it there. It survived anyway.

So the durable class is not "what the compiler checks". The better distinction:

    PRESENCE of a distinguishable element      durable
      a line, an argument, a field, an assertion, a lock type, a constructor choice.
      The spec can NAME it, the draw can be checked for it, and a sibling file that
      mirrors this one carries it across intact.

    MAGNITUDE inside an element that exists either way      NOT durable
      how many times a POST repeats, how many items are seeded. There is no line to be
      present or absent — the test POSTs in both versions. Nothing names it, nothing
      carries it, and mirroring copies the shape while the number rides along unchecked.

That is why prose bought the router arguments, the lock type, the constructor choice and the
raw-body assertion, and did not buy the seed count. It is not about compilers. It is about
whether the thing being asked for is a NOUN the sentence can point at.

AND IT UNIFIES THIS WITH THE ASSERTION-SHAPE FINDING
FINDING-the-only-assertion-rule-is-what-freed-the-setup-count.txt says a per-item assertion
pins the setup and a bare count does not. That is the same law: naming the items CONVERTS A
MAGNITUDE INTO A SET OF PRESENCES.

    len(got) != 2                                    one assertion, a magnitude, unpinned
    got[0].ID=="1" && got[1].ID=="2" && "3" absent   three named things that must be there

Three items become three presences, and presence is the class that survives. lrucache,
taskflow and ratelimit all do exactly this — per-key, per-index, per-ordinal — and all three
got their counts right. The repair proposed in that file is not a trick, then; it is the
general mechanism for making a quantity durable, and it predicts its own success for a
stated reason rather than by analogy.

⚠️ STILL ONE FAILING INSTANCE. taskapipro is the only artifact on the wrong side, and it is
also the only one whose spec forbids extra assertions, so shape and prohibition remain
confounded there. The falsification test is unchanged and unrun: rewrite the entry to name
the items, redraw, and see whether seeds become 3.
