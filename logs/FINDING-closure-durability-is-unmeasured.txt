FINDING — closure durability is unmeasured for four specs and fails for the fifth
==================================================================================
2026-07-26. Set out to audit which of the session's closures are still live. The audit's
first answer was reassuring and wrong.

THE TABLE THAT LOOKED GOOD
      ratelimit   drop Content-Type   CAUGHT
      usersapi    drop Content-Type   CAUGHT
      shortener   drop Content-Type   CAUGHT
      jsonapi     drop Content-Type   CAUGHT
      taskflow    drop Content-Type   SURVIVED   <- regressed

  Read straight, that says four closures held and one broke, and invites the conclusion
  that taskflow is the unstable one.

WHY THAT READING IS WRONG
  ratelimit, usersapi, shortener and jsonapi have exactly ONE green tree each. So
  re-checking "the latest tree" re-checks THE SAME ARTIFACT the closure was graded on. It
  is not independent evidence of anything — it confirms that a measurement taken once is
  still the same measurement.

  taskflow is the only spec with three trees, and it is the only spec where a regression
  could be observed at all. Its Content-Type assertion was written in the first run and in
  neither of the next two:

      taskflow-code       2 Content-Type assertions
      taskflow-projsort   0
      taskflow-errwrap    0

  So the finding is not "taskflow is unstable and the others are stable". It is:

      durability MEASURED for 1 spec of 5 — and there it fails 2 runs out of 3
      durability UNMEASURED for the other 4 — one tree each, nothing to compare

  The four "CAUTGHT" rows carry no information about durability, and I nearly published
  them as if they did. The asymmetry that produced the reassuring table is that taskflow
  got re-run three times because it was the difficult one — so the only spec with enough
  data to show a problem is the one that showed it.

WHAT THIS COSTS THE SESSION'S HEADLINE
  Eight closures were claimed today, each verified on the artifact that closed it. On the
  only spec where durability was actually tested, two of its closures did not survive the
  next run. Whether the other four specs behave like taskflow or not is simply not known,
  and the cheapest way to find out is to re-run one of them unchanged and re-grade — which
  costs one build and would replace an assumption with a number.

  Recorded rather than run now, because a taskflow build is already occupying the fleet.

A SEPARATE OBSERVATION, WORTH KEEPING APART FROM THE DURABILITY RESULT
  jsonapi's first run took 94s and its re-run 293s, same spec and same model. I wrote that
  the first had ZERO fix rounds and the re-run three, and that was wrong — the first run's
  own prediction file records "94s, THREE rounds, no fleet, no escalations". Counted from
  the logs rather than from memory:

      jsonapi-ct  3 rounds, 0 escalations      ratelimit-ct     0 rounds, 0 escalations
      jsonapi-rerun 3 rounds, 0 escalations    ratelimit-rerun  0 rounds, 0 escalations

  Both controlled pairs — the only two specs re-run against an UNCHANGED spec — show the
  IDENTICAL round count. So the work did not vary at all; only the wall clock did, and the
  293s run was launched while a taskflow build was occupying the same three servers.

  That is a better finding than the one it replaces: for a fixed spec, the fix loop did the
  same amount of work both times, and a 3x wall-clock difference was contention rather than
  the model doing more. Cost variance and outcome variance are different questions and I
  had collapsed them by misreading my own record.

  So run-to-run variance is real and large in COST, and on these two small specs it did
  not reach the OUTCOME. That is a different claim from "small specs are stable" and only
  the first half is measured: two specs, two re-runs. It is recorded here mainly so the
  next surprising build time is not read as a signal about correctness.

AND THE mtime CAVEAT MATERIALISED, ON MY OWN EDITS
  Corrected, ratelimit first reported TestContentTypeJSON as intermittent. It is not. The
  eligibility filter uses each tree's newest file mtime as its generation time, and
  generated/ratelimit-v4 — an archive weeks old — carries a timestamp 20 minutes NEWER
  than the spec entry it predates, because today's non-vacuity proofs deleted and restored
  registry.go and reformatted bucket.go inside it.

      archive     22:40    <- weeks old, touched by today's proofs
      fresh tree  22:21    <- generated before it

  An archive dated after a tree generated earlier is the visible symptom, so the tool now
  PRINTS each tree's inferred time. The limitation was documented in the tool's own comment
  before it bit; documenting a limitation does not stop it, and the fix is to make its
  symptom visible rather than to trust the note.
