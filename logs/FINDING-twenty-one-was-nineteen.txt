WHY LIMIT IS INERT AND OFFSET IS NOT

Both wrong values are 7777. The asymmetry is one layer down, in paginate:

    if offset >= len(items)                     { return []T{} }
    if limit <= 0 || limit > len(items)-offset  { limit = len(items) - offset }

A wrong LIMIT of 7777 hits the second guard and comes back as len-offset — the same number
a limit of 0 produces through the FIRST half of the same condition. Two routes to one value;
no response can differ. A wrong OFFSET of 7777 hits the first guard and returns empty, which
any count assertion sees.

This is the third variant of one thing: a guard behind a guard. taskflow's empty list needed
BOTH the store's make() and paginate's []T{} broken before anything changed. Here the second
guard is not redundant, it is ABSORBING — it maps every wrong value to the right one. Same
consequence for a single-site mutation: structurally invisible.

THE TOOL COULD NOT HAVE REPORTED THESE — TWICE OVER

First, addressing. A string needle in the probe registry means "flip the boundary operator on
that line", and a clamp body has no operator: `limit = 0` is an assignment. The registry
needed a VALUE mutator with per-occurrence selection before the question could be asked at
all. Without it the eight sites are four rows, and four rows cannot show a 2/2 split.

Second, and worse: the OBSERVABLE / DEFENDED-ALREADY split was decided by a HARDCODED LIST of
probe names —

    if any(name in note for name in ("TestChain", "TestValidateRejectsZero", "TestPaginate",
                                     "TestClearOutOfRange", ...)):
        return "OBSERVABLE"
    return "DEFENDED-ALREADY"

Every name on it was one of mine, so it was correct the day it was written and structurally
incapable of staying correct. The ninth probe, added today, is called
TestClampValueIsObservable. It matched nothing. Both real holes above were first reported
DEFENDED-ALREADY — "the artifact's own suite sees this", about a test the artifact does not
contain — and I nearly filed that as "the rows were stale, nothing to close".

A stale allowlist fails toward NOTHING TO SEE HERE, which is the direction that ends an
investigation. This is the third time the same shape has cost something in this repo:
_corpus_state's writer list went stale the first time it was tested (four new drivers
invisible), and _hole_hunt's self-test dispatched at module level and ran another tool's
fixtures. The rule those two already paid for: a tool must DERIVE what it knows about
itself. The classifier now reads the probe's own function names out of the probe source.

Pinned: a fifth self-test case whose probe is named TestNameNoAllowlistKnows. Verified by
reverting ONLY the classifier and keeping the pin — the old code fails it with the exact
misclassification found in the live data. (The first attempt at that check stashed both the
fix and the pin and passed trivially, which measures nothing.)

WHAT THIS DOES NOT CHANGE

Nothing about the closures already graded. The negative-offset clamps in both files are the
two sites this week's spec edits target, and they are exactly the two that are real: draw 2
closed tasks.go and draw 3 is generating the projects.go twin now. The correction removes two
rows I should never have counted; it does not remove a closure, and no graded CAUGHT verdict
moves.

The honest sentence: the capstone's method section says a hole must pass three tests —
applied, observable, reachable — and that checking only the first reports 48 while checking
all three reports 21. Four rows in its own final table were never put through the second one.
The method was right. I stopped applying it one row short of the table it produced.
