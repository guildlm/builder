PREREG — repeat the parity pair across SERVER PROCESSES, which is the unit that actually varies
================================================================================================
31 July, written while the mis-designed version is still finishing. Supersedes the replication design
in logs/PREREG-withhold-the-parity-clause-from-an-interface-only-file.txt; the ENDPOINT and REJECT
conditions there stand unchanged.

WHY THE FIRST DESIGN WAS WRONG, measured rather than suspected
    Both parity controls produced BYTE-IDENTICAL projects — 19 files, two processes, 100 minutes
    apart. The whole pipeline is a deterministic function of (spec, flags, server process).

    So "3 pairs" was three copies of one observation. Meanwhile the campaign has measured that the
    SAME prompt in a DIFFERENT server process yields different files — today, by rendering the
    pre-today and post-today prompts for store.go and finding them byte-identical while the archived
    and fresh outputs differ. Process is the variance; draw is not.

THE CORRECTED DESIGN
    For i in 1..3:
        restart mlx_lm.server (fresh process, same model)
        draw CONTROL  (GUILDLM_ENABLE_RULES='')                     on specs/ledger-origorder.yaml
        draw ARM      (GUILDLM_ENABLE_RULES='interface_only_scope') SAME process, same flags
        record the pid with both rows

    Same six draws, same cost. The pair stays inside one process — that is what makes it a controlled
    comparison — and the REPLICATION crosses processes, which is what makes three of them worth more
    than one.

    ⚠️ The pair must not straddle a restart. That is the one thing this design can get wrong, and it
    is the same requirement the campaign already enforces with `_server_pid.sh` for reused controls.

SCORING
    PRIMARY   the control/arm difference (control SPLIT, arm CONSOLIDATED) reproduces in all three
              processes. Predicted 2 of 3, confidence 50%.

    ⚠️ 50% IS NOT HEDGING, IT IS THE HONEST NUMBER. I have exactly one process's worth of evidence
    and a documented history of process-level variation changing outcomes for identical inputs. A
    higher number would be borrowed from the byte-identical replication, which measures the pipeline
    rather than the effect.

    REJECT    if control and arm AGREE in any process — both SPLIT or both CONSOLIDATED — the effect
              is process-dependent and the single-process result must be reported as such, not as
              "the parity clause prevents consolidation".

    NOT AN ENDPOINT   convergence (rc). arm-1 failed to converge and both controls went green, but
              four files differ between the conditions and the failure could originate in any of
              them. Recorded, never interpreted.

WHAT IT STILL CANNOT REACH
    One spec. ledger-origorder only. The cross-spec measurement today put workapi at a far higher
    consolidation rate and showed that ledger's clean bimodality does not generalise, so nothing here
    licenses a claim about specs other than this one.

    ⚠️ AND IT CANNOT RUN YET. `src/builder.py` and `_parity_ab.sh` are frozen until the current pairs
    finish — every draw is a fresh process that re-reads the harness, and bash reads a running script
    incrementally. The queue after the run is: HEAD guard, app-log normalisation, stripper logging,
    then this.

COST OF THE RESTART, measured so the design is not rejected on a guess
    From logs/mlx-server-0731.out, this morning's start:
        httpd up            10:08:30
        first inference     10:09:09
        gap                 39 seconds  (model already in the HF cache — "Fetching 9 files" was
                                         instant, so this is load-into-memory, not download)

    Three restarts -> about 2 minutes of overhead across the whole experiment.

    Against six draws that cost 20 to 77 minutes each — measured today: ctl 19.3 and 30.1 min, arm-1
    77.0 min — the restart is under 1% of the run. There is no cost argument for keeping the broken
    replication unit, which is worth stating because "restarting the server between pairs is
    expensive" is exactly the kind of plausible objection that would have gone unchecked.

    ⚠️ The 39s assumes a warm HF cache. A first-ever load of a model would download weights and take
    far longer; every process in this experiment uses the same model that is already cached.

PRIOR REVISED — on evidence that existed before I set it, and which I had not read
════════════════════════════════════════════════════════════════════════════════════════════
logs/RESULT-process-identity-is-the-variable-and-the-boot-is-not.txt (30 July) contains two facts
that bear directly on this design, and I set the 50% without either.

    1. CROSS-PROCESS VARIATION IS LARGE. "Three processes, three distinct programs, mutually 3, 4 and
       6 CODE files apart." And "two functions that no spec edit ever moved were moved by changing
       nothing but the pid." So a fresh process does not perturb the output slightly — it rewrites
       several files.

    2. NO ARM IN THIS CAMPAIGN HAS EVER CROSSED THE PROCESS BOUNDARY. "Every one of those arms was
       control-vs-arm inside ONE process ... Everything here happens BETWEEN processes, a boundary no
       arm in that series ever crossed."

       ⚠️ THIS DESIGN WOULD BE THE FIRST. That is the point of it, and it is also a warning: the pair
       stays inside a process (correct), but the REPLICATION crosses a boundary that has never been
       crossed with a manipulation attached, and cross-process variation is measured at 3-6 files.

REVISED PREDICTION
    The control/arm difference reproduces in all three processes: 35%, down from 50%.
    Reason: the effect is one sentence changing one file, and a process change independently rewrites
    3 to 6 files. If store.go is among the volatile set in some process, the control itself can
    consolidate there — which is my REJECT condition, and it is now a live outcome rather than a
    formality.

    ⚠️ REVISED BEFORE THE RUN, ON PRIOR EVIDENCE, NOT AFTER SEEING ANYTHING. The distinction matters
    and this is the legitimate case: new-to-me evidence that predates my prediction. Had I read the
    directory first, 35% is the number I would have written.

    AND THE CAMPAIGN'S OWN LEDGER ARGUES FOR HUMILITY: that same file records nine predictions with
    three hits. A 35% on a first-ever boundary crossing is not pessimism.

WHAT THE CORRECTED RUN WILL COST, from today's actual durations
    completed draws today:
        ctl-1  30.1 min   arm-1  77.0 min
        ctl-2  19.3 min   arm-2  82.2 min
        ctl-3  30.4 min   arm-3  running (arms have taken 77.0 and 82.2)

        5 draws · 239 min · projected 6-draw total ~319 min (5.3 hours)

    The corrected design runs the SAME six draws plus three server restarts at 39s each:
    ~321 minutes. The restarts are 0.6% of the run, which is the number the earlier note predicted
    and now has today's own durations behind it rather than an estimate.

    ⚠️ AND THE COST IS ASYMMETRIC BY CONDITION, which matters for scheduling. Controls converge in
    fix round 1 and take 19-30 min. Arms exhaust 8 rounds and take 77-82. So the arm draws are 72%
    of the wall clock, and any decision to shorten the experiment should cut arm draws, not pairs —
    cutting a pair removes one control AND one arm, which is the only unit that answers anything.

    ⚠️ AND IF THE TIMESTAMP NORMALISATION LANDS FIRST, the arms should get cheaper: 5 of their 8
    surfaces collapse under the fix (measured on arm-1's real output), so the repeat detector would
    stop them at round 3 or 4 rather than granting all three extension rounds. That is ~20 minutes
    per arm, ~60 minutes off the corrected run — the first concrete reason to keep the queue in its
    current order beyond correctness.

THE FREEZE GUARD, SPECIFIED BY MEASUREMENT RATHER THAN BY NAME
    Queue item 1 was written as "add a git HEAD guard". Tested whether HEAD is the right thing to
    check by appending a comment to src/builder.py mid-check:

        HEAD              247e980  ->  247e980      UNCHANGED
        builder.py sha    53dde9f  ->  1ce2998      CHANGED
        git status src/   ''       ->  ' M src/builder.py'

    So a HEAD comparison would MISS an uncommitted edit entirely, and today's freeze was exactly the
    situation where that matters: a one-line logging change, applied and not yet committed, would
    have slipped past a HEAD guard and landed in draws 4-6 of a six-draw experiment.

    THE GUARD IS THEREFORE: hash `src/builder.py` and the runner itself at start, re-check before
    every draw, refuse on any difference. Not HEAD — HEAD is a proxy that fails in the direction that
    costs the experiment.

    ⚠️ `git status --porcelain src/` also catches it and reads more naturally, but it answers "is the
    tree dirty", not "is it the same as when I started". A file edited and then reverted to a
    DIFFERENT commit's content would show clean while being wrong. The hash answers the question that
    is actually being asked.

    Cost: one shasum per draw, against draws that take 19 to 82 minutes.

RESTART MECHANISM PRE-FLIGHTED against the live server
    readiness probe   curl -s -m 3 http://localhost:8080/v1/models   ->  responds in 0.157s
    _server_pid.sh    7598        pgrep -f mlx_lm.server   7598      ->  agree

    So the runner's between-pair sequence is: read the pid with `./_server_pid.sh` (NOT lsof — colima
    binds 8080 too), kill it, relaunch with the same --model, then poll /v1/models until it answers.
    Observed cold-start-to-first-inference this morning: 39 seconds.

    ⚠️ THE PROBE ANSWERS BEFORE THE MODEL IS LOADED. /v1/models is served by the HTTP layer and, as
    established today, LISTS THE HF CACHE rather than the loaded model — it returned
    Qwen2.5-3B-Instruct while the 7B coder was serving. So "responds" means the socket is up, not that
    inference is ready.

    The honest readiness signal is the first completion, not the first 200. The runner should either
    wait for the startup log's model-fetch line, or simply issue a tiny completion and wait for it —
    the second is self-validating and costs one short generation.

    ⚠️ Recorded because "poll the health endpoint until it answers" is the obvious implementation and
    it would start a draw against a server that is still loading weights, producing a first draw that
    differs from the rest of its pair for reasons that have nothing to do with the manipulation. That
    is the same class as every confound corrected today, and it is cheapest to avoid before writing
    the runner.
