FINDING — gate-chain re-mining over the archived _fail-* corpus (2026-07-24)
==============================================================================

METHOD (model-free): the archived red projects in generated/_fail-* are failures the
builder gave up on WHEN THEY WERE MADE. The deterministic gate chain has grown to 30+
gates since. So re-run the CURRENT chain to a fixpoint over each old failure and see what
it now fixes vs what it still cannot — "whatever it still cannot fix is the backlog"
(tests/test_three_small_gates.py docstring). No model, only go vet + _run_deterministic_gates.

RESULT over 18 _fail-* archives:
  - 15/18 are now GREEN under the current chain. The gates added since these failed
    (self-qualifier, negated-comparison, slice-equal, external-test-package, arity,
    struct-literal-key, ... ) retroactively repair them. This is a strong, concrete
    validation of the whole gate campaign: real historical failures, fixed deterministically.
  - 3/18 remain RED, all with the SAME error:
        vet: ./shortener_test.go:58:36: not enough arguments in call to doReq
    doReq(t, h, method, path, token, body) takes 6 params; the GET-request calls omit the
    trailing `body` (5 args). One recurring mechanical shape.

WHY THIS ONE IS NOT ADDED AS A GATE (the honest call):
  A gate for "not enough arguments" would have to append a value for the missing parameter.
  That is a GUESS, not a single meaning — the two properties the gate philosophy separates
  ("exactly one meaning ... is what separates them from a guess"). Worse, a wrong value
  compiles but fails an ASSERTION, which reads as a model logic bug rather than a mechanical
  one — so a value-guessing gate can actively MISLEAD the fix loop (do harm). Positionally
  the fix is "append the last param's zero value", and for this case ("" for a GET body) it
  is even semantically right, but the gate cannot know that in general. So this gap belongs
  to the MODEL (or a risk-accepting heuristic), not to the deterministic chain.

SECOND PASS — the other families (taskapipro / workapi / taskflow / tasks-api), 29 archives:
  - 20/29 now GREEN under the current chain.
  - 9 remain red, and NONE is a clean recurring gate shape: one is a SYNTAX error
    (`missing ',' in argument list` — malformed generation, model-shaped), the rest fail on
    something other than a compile error the keyword scan recognises (test assertions /
    runtime — compiles-but-wrong, which is the model's job, not the gate's).

COMBINED (47 archives): ~35 now GREEN under the current chain (~74% of the historical
backlog, deterministically), and the remaining ~12 are all MODEL-shaped — arity/value
guesses, raw syntax breakage, or wrong-behaviour assertions. No further clean, single-meaning
gate emerged from the corpus.

TAKEAWAY: the deterministic gate chain is in good shape — it clears ~35/47 of the archived
backlog on its own. The residual tail is deliberately model-shaped (a gate for it would have
to guess). This is a NEGATIVE result on "mine the corpus for another gate" and a strong
POSITIVE result on "is the chain effective". The one clean gate added this session
(external-test-package) came from a LIVE demo, not this corpus — new gate shapes come from
NEW failure modes (fresh runs), not from re-mining a backlog the chain has already grown to
cover. So the gate-mining vein is exhausted; the next gate will come from a new failing run.

ADDENDUM 2026-07-25 — the tool that produced this had a measurement bug.
  The headline SURVIVES; a number this finding never printed did not.

  _gate_audit.py decided its "advanced" verdict by comparing the toolchain's OUTPUT
  before and after the gate chain. That output is not a function of the code: the same
  unchanged tree, checked twice, differs in goroutine ids, heap addresses and durations.
  Every artifact whose tests PANIC therefore compared unequal to itself and was scored
  "advanced" with no gate having fired. Both modes carried it (audit() and --regress);
  both are fixed (builder 5ba77de, 0cbea6b) and the fixpoint driver is now one function
  (c6b70fe) so a third copy cannot drift. The code's own comment already said the status
  was "derived by DIFFING (did the tree change)" — that is now what it does.

  MEASURED IMPACT, same 12 archives, old tool vs fixed:
      old      1 green ·  8 advanced ·  3 stuck   (43s)
      fixed    1 green ·  0 advanced · 11 stuck   (21s)
      the GREEN set is byte-identical between the two.
  So the inflation was large — 8 of 12 "advanced" verdicts were artifacts nothing had
  touched — and it lands entirely on a bucket this finding does not use. The ~35/47
  headline is a `green` count, which comes from a real toolchain verdict, and it stands.

  ONE CLARIFICATION THIS FINDING DOES OWE THE READER. Its METHOD line says "no model,
  only go vet + _run_deterministic_gates", so its "GREEN" means the compile/vet stratum
  is clear. The Builder's own gate — and _gate_audit --regress — is build+vet+TEST, and
  by that criterion the same corpus reports 11/44. Both are true of different questions:
  the gates repair MECHANICAL breakage, and a project can compile and vet cleanly while
  its generated tests still fail on behaviour no gate can supply. Read "~35/47 clear the
  chain" as a statement about compile/vet, never as "these projects now pass".
  (--regress now prints the stratum each artifact reaches, so the two cannot be confused
  again: builder bbe8052.)

ADDENDUM 2 (2026-07-25) — re-derived with the corrected, filtered tool.
  The conclusion holds, and now rests on a cleaner instrument than the one that
  produced it.

  The audit's default mode had been walking every directory under generated/, which
  includes ~190 hand-built fixtures for other experiments (_bitset-BEFORE,
  _eventbus-AFTER, _iso-*, _cachefix-*), several of them green ON PURPOSE. That
  polluted the very ranking this finding is about: question 2 buckets residual
  diagnostics to choose the next gate, and it was being fed code no model ever failed
  on. Both modes now share one corpus selector (builder 4d2f0a5), and the "advanced"
  verdict no longer compares run-varying toolchain output (5ba77de, 0cbea6b).

  RE-RUN over the 44 real archived failures:
      8  still do not COMPILE          -> a gate could still help
     36  compile, but a TEST fails     -> only the spec or the model can

  RESIDUAL COMPILE CLASSES, by distinct specs affected:
      2  not enough arguments in call to X
      1  cannot use X(X(X())) (*X) as service.X — does not implement
      1  missing ',' in argument list
      1  cannot use X(store) (http.X) as *http.X in return: need type assertion
      1  undefined: X

  READ IT: the only shape recurring across more than one spec is the arity gap this
  finding already refused on purpose, because filling it means GUESSING a value and a
  wrong guess compiles, fails an assertion, and misleads the fix loop. Everything else
  is a single-spec one-off. And 36 of 44 residual failures are not compile errors at
  all — they are behaviour, where no gate can reach.

  So "the gate-mining vein is exhausted" was right, and it is now the reading of an
  instrument that is not quietly inflating its own progress. Two independent tools
  also agree on how much the chain clears: this audit and _escalation_surface.py both
  report 11 artifacts reaching build+vet+test green, which is the criterion this
  finding's headline (~35/47) does NOT use — that one counts the vet stratum, as its
  METHOD line says. Both numbers are right about different questions.

  (Artifact counts differ by one between the tools by design: this audit includes
  _proof-* archives, _escalation_surface.py globs _fail-* only. Both exclude the
  go.mod-only shells.)
