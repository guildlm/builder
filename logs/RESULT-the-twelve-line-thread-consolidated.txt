RESULT — the twelve-line investigation, consolidated
=====================================================

18:30 on 29 July. This thread now spans six files and three retractions. Written so a reader
does not have to reconstruct it from the order things were discovered in, and so the OPEN
questions are separable from the settled ones.

THE ORIGINAL CLAIM (15:58): adding twelve lines to taskapipro's projects test entry caused
three implementation files to lose their module prefix, broke the paging twins, and cost the
capstone 62 rows.


WHAT IS ESTABLISHED
====================

1. THE CONTENT OF THE TWELVE LINES IS IRRELEVANT TO EVERYTHING MEASURABLE.
   Twelve lines of prose about naming a variable `t` produce the same result as twelve lines
   about page sizes and store contents:
     · the same round-1 import defect, byte for byte
     · the same defect at the same line AND column in rounds 3 and 4
     · all six fix rounds identical — the same error STRINGS and the same files repaired in
       the same order
     · the generated code identical bar one comment's word order and one Fatalf message
   Basis: the inert control arm (drawn 16:41-18:15) against both v5 draws.

2. THEIR PRESENCE CHANGES GENERATED CODE IN FILES THE ENTRY NEVER MENTIONS.
   On one denominator — the seven files untouched in all four draws:
     v5 draw1 vs draw2   differ by nothing           0 of 7
     inert vs v5         differ by CONTENT           1 of 7   a comment
     chain5 vs v5        differ by PRESENCE          4 of 7   3 CODE + 1 PROSE
   chain5 carries an entire `getenv` helper in internal/config/config.go that v5 does not, and
   service.go differs in a statement body. ⚠️ Refined 19:30: of the four, THREE are genuine
   code differences (config.go, service.go, models_test.go) and one — middleware_chain_test.go
   — differs only in comments or strings. An earlier version said all four were code.

3. AND THAT EXPLAINS THE DEFECT LINE NUMBERS RATHER THAN CORRELATING WITH THEM.
   chain5's mirrored-argument defect sits at projects.go 77:55 and its half-repair at 56:2.
   Both v5 draws and the inert draw put them at 71:55 and 50:2 — a constant six-line offset,
   because the arms contain different code above both sites. The inert draw matches v5 to the
   column because it IS v5's code.

4. SAMPLING VARIANCE IN THIS CONDITION IS ZERO, which is what makes 1, 2 and 3 readable at
   all. Two v5 draws four hours apart on one server: 8 of 8 untouched files identical.


5. IT IS THE SPEC, NOT THE SERVER (answered 19:21). The pristine pre-edit draw on 4439 wrote CORRECT
   prefixed imports (all 5, read from .pre-fix.json), against UNPREFIXED in both +12 draws and
   the inert arm on the same server. Server held fixed, spec the only difference. The draw ALSO
   graded UNMEASURED on compiler output — chain5's masking, reproduced exactly as predicted at
   18:10 — so the snapshot is the only reason it answered. And it reproduces chain5 on all 7
   untouched files, which fills chain5's hole in the table.
   See RESULT-the-twelve-lines-cause-the-import-defect.txt.
   ⚠️ The STUB-FILE regression is NOT this: chain5 and the pre-edit draw both leave
   internal/store/memory.go empty, so that stays open and separate.


WHAT IS SUGGESTIVE AND NOT ESTABLISHED
=======================================

6. A ONE-LINE EDIT IS SURGICAL WHERE TWELVE ADDED LINES ARE NOT.
   taskflow's rename (11520cc), draws either side on the same server: 11 of 12 untouched files
   identical, and the twelfth is the file the rename is about, differing by exactly the renamed
   function.
   ⚠️ DIFFERENT SPECS. taskflow for the one-line arm, taskapipro for the twelve-line arm. A
   one-line change to taskapipro has never been drawn and neither has a twelve-line addition to
   taskflow. Suggestive of a dose relationship; not a measurement of one.
   ⚠️ THE SETTLING EXPERIMENT IS CHEAP: twelve inert lines into a taskflow entry. taskflow
   converges in one round.
