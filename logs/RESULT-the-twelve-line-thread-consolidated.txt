    taskflow    control      chain5 vs chain6       12 of 12 identical
    ratelimit   +48 arm      dose vs dose2           6 of 6 identical, ALL 5 ROUNDS identical

    Thirty-three files, not one byte different. The ratelimit pair is the only TREATMENT pair
    and it matters: until 21:42 zero-variance was established for controls only, leaving open

    THEREFORE every difference below is a difference BETWEEN conditions, never within one.
    That is what makes n=1 arms readable at all.

⚠️ NOT UNIVERSAL. `_iso-workapi-without` diverged in 1 of 3 draws — one group in five. The
zero is a property of the conditions measured, not a law.

IV-b. AND IT IS ABOUT LENGTH, NOT DOSE — five arms on taskflow
==============================================================
All five against the same control condition, as-drawn where snapshots allow:

    same-length SUBSTITUTION  (rename, 21 -> 21 chars)   CODE 1 — the TARGET only, NO collateral
    same-length SUBSTITUTION  (rename, 19 -> 19 chars)   CODE 1 — the TARGET only, NO collateral
    +1  ADDITION                                         CODE 3 — target + 2 collateral
    +3  ADDITION                                         CODE 8
    +12 ADDITION                                         CODE 6

    TWO substitutions, two entries, two test names: no collateral either time. THREE additions,
    the smallest a SINGLE LINE: collateral every time.

    IT IS NOT A DOSE. Three lines perturbed EIGHT files where twelve perturbed six, and the
    perturbed SETS differ rather than nesting — five files move at both, three only at +3, one
    only at +12. Adding more is not reliably worse; adding ANY is worse than adding none. A
    step at zero, and noise above it.

    IT IS NOT A FLOOR EITHER. One line was the smallest addition available and it still
    reached router.go and taskflow_test.go, neither of which it mentions.

    LENGTH IS THE VARIABLE. The only arms without collateral are the only arms that did not
    change the spec's byte count.

THE RULE, AS MEASURED
    · a substitution preserving the spec's byte count leaves the rest of the program alone
    · ANY addition, down to one line, re-decides files the edit does not mention
    · so there is no SIZE budget. There is a KIND budget.

⚠️ WHERE IT IS THIN. Both safe arms are word-order swaps of a TEST NAME, so meaning is
preserved as well as length. A same-length change that ALTERS meaning is untested —
`sorted by ID` -> `sorted by id` is equal length and means something else — so "preserves byte
count" may be standing in for "preserves meaning and structure". And five single draws on one
spec: each arm is real because same-condition variance here is zero, but the shape is five
points from five draws.


V. WHAT THIS DOES TO THE CAMPAIGN'S OWN HEADLINE
=================================================
"Redraw drift is worth about 6 up and 2 down" was measured across a corpus whose flip-bearing
specs the campaign had itself rewritten:

    specs that grew >=40 lines   6 artifacts · 107 live rows · 8 flips   7.5%
    specs that grew  <40 lines   8 artifacts ·  33 live rows · 0 flips   0.0%

    All eight flips are in specs that grew 43-73 lines; none in the 33 rows whose specs were
    untouched. With the spec held constant the observed drift is zero, which is what every
    pair in section I shows.

    SO SIX-UP-AND-TWO-DOWN IS NOT REDRAW DRIFT. It is spec-edit drift, and the baseline for
    what a redraw moves on its own should be closer to zero.

✅ AND IV-b GIVES THE FIRST USABLE SPLIT OF THE CAMPAIGN'S OWN RESULTS. Its closure edits ADDED
43-73 lines per spec, so all of them are in the perturbing class and those before/after
comparisons cannot separate closure from re-decision. But its PURE RENAMES are in the safe
class — including the taskflow rename that produced this thread's cleanest single-variable
result — and those measurements stand.

⚠️ CONFOUNDED BEYOND REPAIR FROM THIS DATA. The specs grew BECAUSE closures were added, so
"grew" and "the campaign worked on it" are the same set. A taskflow flip may be the closure
taking effect or 73 added lines perturbing an unrelated file. THE CAMPAIGN CANNOT DISTINGUISH
ITS SUCCESSES FROM ITS OWN PERTURBATION.

⚠️ AND PERTURBING A FILE DOES FLIP A VERDICT — measured 22:18, on the artifact it needed to be
measured on. See section V-b.


V-b. GROWTH MOVES VERDICTS, AND A VERDICT IS NOT A FACT ABOUT ITS OWN FILE
===========================================================================
Three artifacts were asked whether perturbation reaches a mutation verdict:

    jsoncodec +12   green · impl file rewritten · 0 of 6 verdicts moved
    jsoncodec +24   green · rewritten MORE      · 0 of 6 verdicts moved
    ratelimit +48   RED   · unmeasurable, every row BASELINE-RED
    taskflow  +12   green · 49 rows, 19 shapes  · TWO verdicts moved

    taskflow is the one that could answer it. jsoncodec's six rows are two shapes in one file;
    taskflow has nineteen shapes across a dozen.

    models.go   %w -> %v (ErrValidation)
    control   CAUGHT · SURVIVED · SURVIVED      dose   CAUGHT · CAUGHT · CAUGHT

    And the site count changed too: projects_handler.go and tasks_handler.go each gained a
    StatusInternalServerError site, 3 -> 4. Twelve inert lines changed how many things there
    are to defend.

THE MECHANISM, which is the part that matters
models.go differs between the arms by EXACTLY TWO COMMENTS. Comments cannot change behaviour,
so the verdict change does not come from the mutated file — it comes from the rest of the
program. Confirmed as-drawn (chain6 vs dose, both snapshotted, before either fix loop ran):
16 files, CODE 6, and TWO of the six are TEST files — taskflow_test.go and pagination_test.go.

    The model wrote different TESTS. The chain is: twelve inert lines -> different tests
    -> different verdicts, and every link is measured before any repair.

    A MUTATION VERDICT IS A PROPERTY OF THE WHOLE PROGRAM, NOT OF THE MUTATED FILE. Every
    capstone row is keyed (artifact, FILE, shape, ordinal) and read as a statement about that
    file's defences. A flip attributed to a closure in file X can be caused by an edit that
    never touched X.

⚠️ ONE PAIR, ONE DOSE. Two SURVIVED becoming CAUGHT is the direction a closure campaign WANTS,
which is exactly why it is dangerous: this pair got that result from prose that closes nothing.


VI. TWO NEIGHBOURING FINDINGS, NOT ABOUT THE TWELVE LINES
==========================================================
THE STUB REGRESSION TRACKS THE SERVER. Six draws on process 4439 across THREE specs leave
`internal/store/memory.go` as a bare `package store`; four draws on other processes are correct
AND byte-identical to each other. The four 4439 taskapipro draws span both spec states, so the

rather than "empty files".
    ⚠️ server and day are not separated: 4439 started 09:29 on 29 July.

THE SPEC ASKED FOR A STRUCT AND EVERY DRAW BUILT AN INTERFACE. taskflow's store entry says "A

second type the spec never mentions. All converged GREEN. `_shape_conformance.py`: 51 checked,
2 flagged, no false positives.

VIII. WHAT WAS RETRACTED, AND THE ONE ERROR BEHIND MOST OF IT
==============================================================
  * "the loop repairs the wrong side"           rounds 1 and 2 targeted projects_test.go
  * "the edit broke the tasks twins 3,3 -> 1,2" post-repair tree vs near-as-drawn tree
  * "chain5 genuinely lacks undefined: w"       it lacks it AT ROUND 2, after four fixes
  * "generation is deterministic"               one group in five breaks it
  * "chain5 vs v5 differ in 4 REAL CODE files"  three CODE, one PROSE
  * "nothing globs generated/ broadly"          _cross_draw does

The first three are one error: A QUANTITY READ OFF A GENERATED TREE IS A POST-REPAIR QUANTITY.
Sections I-IV avoid it by comparing only files no draw repaired, or by reading `.pre-fix.json`.
That constraint is why the established list is as short as it is.
