FINDING — six measurement bugs in one day, all of them in the instruments
=========================================================================
2026-07-25, model-free. Not a bug report; a pattern report, written because the pattern
predicts where the next one is.

WHAT HAPPENED
  A day spent testing one hypothesis (escalate only blamed files) turned up six defects.
  Every single one was in a tool that MEASURES the builder. None was in src/builder.py.

    1. _gate_audit.audit()      "advanced" decided by comparing toolchain OUTPUT across
                                two runs. That output is not a function of the code —
                                heap addresses, goroutine ids, durations all move — so
                                every artifact whose tests panic scored as progress with
                                no gate having fired. Its own comment said it diffed the
                                TREE.
    2. _gate_audit --regress    The same defect, second copy, same file. Its printed
                                explanation says "STUCK means the gates changed NOTHING".
    3. audit_mechanisms         Claims to check "every run we have ever done"; globbed
                                logs/ab-*.log only, so any mechanism exercised by a run
                                under another filename read as NEVER FIRED. It reported
                                the fleet escalation dead on the day it shipped.
    4. _gate_audit default      Header says the corpus is failed builder runs; walked all
                                of generated/, including ~190 hand-built fixtures, several
                                green on purpose — polluting the ranking used to pick the
                                next gate.
    5. _escalation_surface      Counted go.mod-only kill-debris archives as "unattributed
                                errors", which was the last surviving argument for the
                                hypothesis I was testing. My own debris, read back as
                                evidence for my own claim.
    6. project_bench            Compares before/after by BASENAME, so two packages holding
                                a handler.go shadow each other and an edit to the shadowed
                                one reads as "nothing changed". Latent — no bench project
                                repeats a basename today.

THE ASYMMETRY IS THE FINDING
  src/builder.py has 363 tests. The instruments had none, and still have almost none. Yet
  the instruments are what every claim in logs/FINDING-*.txt rests on. The project applied
  "prove it fires" rigorously to its GATES and never once to the tools that grade them.

  Three of the six (1, 2, 4) are the same shape twice over: a helper written in two places,
  with the fix needed separately in each. Two (1, 3) are a comment that describes the
  intended behaviour while the code does something else — and in both the comment was
  RIGHT, which means the defect was one careful reading away the whole time.
  One (5) is the most dangerous kind on offer: a measurement error whose direction happened
  to support the hypothesis under test.

  Failure mode in one line: an instrument that is wrong does not error. It prints a
  plausible table.

WHERE THE NEXT ONE IS — the instruments that could not be caught being wrong
  Ranked by damage if silently wrong. Same day, the top three were closed; what each
  self-test is worth is stated by what it catches when the historical defect is put back.

    tool                     self-test   what a planted defect proves
    score_backend.py         ADDED       a suite that passes while asserting nothing is
                                         not credited (removing the demotion scores it 3)
    _teeth_suite.py          ADDED       a red baseline voids the verdict instead of
                                         reporting a fake CAUGHT (the mistake that cost
                                         four by-hand runs)
    _named_test_audit.py     ADDED       a substring is not a match — restoring the
                                         original `name in blob` fails the check
    _gate_audit.py           ADDED       an untouched tree reports untouched; one check
                                         is taken, not two; one corpus selector, one
                                         gate driver
    _escalation_surface.py   ADDED       the widening is still visible; kill-debris is
                                         excluded
    _deadlock_detector.py    none        its logic (mutex_self_deadlock) IS in the pytest
                                         suite, so it is the one already covered
    project_bench.py         none        needs a coder to run; its latent basename defect
                                         is fixed, the harness remains unchecked
    _unrouted_compat.py      none        it IS a differ — its output is two dumps compared
                                         by hand, with little room to be quietly wrong

  So the gap is closed where it was worth closing, and the two that remain are named with
  the reason rather than left on a list.

WHAT NOT TO CONCLUDE
  Not "add self-tests everywhere". Two of today's six would not have been caught by a
  self-test at all — #3 and #4 are corpus-selection mistakes, where the tool does exactly
  what it was told over the wrong input, and a planted-defect fixture passes happily. Those
  were caught by reading the docstring against the code, which is cheaper than it sounds
  and worked four times today.

  The rule that generalises: when an instrument's PROSE and its CODE disagree, the prose is
  usually the intent and the code is usually the bug. Read them against each other before
  trusting a number, and never trust a number that arrived in the direction you wanted.

ADDENDUM, same day — the pattern is not about old code or other people

  The six above were found in instruments written weeks earlier. Later the same day it
  happened twice more, in tools I wrote MYSELF, hours after writing this finding, while
  actively looking for exactly this:

    _hole_closed.py    Generalised from a taskflow one-off. The patch changed the code and
                       silently failed to replace the docstring, so the committed file
                       described itself as grading one specific prediction while the code
                       already took a spec argument. My COMMIT MESSAGE went further and
                       quoted a usage line with a `--drop-header` flag that exists nowhere.
    _hole_hunt.py      Gained a second mutation shape, an --all-sites mode and a
                       --self-test in three commits. Its header still announced one shape,
                       one invocation, and a conclusion from "the first run" that two later
                       runs had superseded.

  Neither failed. Neither errored. Both would have been read as documentation.

  WHAT THAT CHANGES ABOUT THE CONCLUSION
    The original framing — instruments are unmeasured, add self-tests — is right and
    insufficient. A self-test cannot catch a docstring, and both of these tools HAVE
    self-tests that passed the whole time. The mechanism is simpler and more stubborn: a
    docstring is written once, at the moment of most understanding, and then the code moves
    and nothing pulls the prose along. Every edit is individually too small to justify
    re-reading the header.

    The cheap discipline that actually worked, four times today: after changing a tool,
    read its own header back against what it now does. It found two of my own defects
    inside an hour and cost about a minute each. It is the same instinct as the gate
    campaign's "prove it fires", applied to prose instead of behaviour — with the
    difference that nothing can automate it, because the thing being checked is whether two
    descriptions of the same thing still agree.

---------------------------------------------------------------------------
ADDENDUM 2 — a SECOND recurring pattern, and it is worse than the first

  The prose-vs-code defects above are embarrassing but loud once seen. This one is quiet:
  three times in one day, in one tool, I sampled ONE site and reported a clean sweep.

    1. _hole_hunt shapes 1-2: probed the first mutable site per artifact. Adding
       --all-sites found 3 more survivors, two of them genuine holes — half the total.
    2. shape 3 (sort order): the comparator regex was anchored to the whole line, and five
       of the six comparators in the corpus are written inline
       (`sort.Slice(out, func(i, j int) bool { return out[i].ID < out[j].ID })`). It probed
       ONE site of six and reported a clean sweep — in a shape added to fix under-sampling.
    3. shape 4 (error wrapping): probed the first `%w` per file. taskflow's models.go
       wraps ErrValidation three times and defends two; tasks-api defends ErrNotFound four
       times and ErrInvalidTask never. One-site probing reports whichever it lands on.

  WHY IT IS WORSE THAN THE PROSE DEFECTS
    A wrong docstring is discovered by anyone who reads the code next to it. Under-sampling
    produces a NUMBER, and the number is always in the flattering direction: fewer holes,
    cleaner corpus, campaign closer to done. Nothing looks wrong. The tool ran, the table
    printed, every row was correct — and the rows that were never generated are the answer.

    It is the same failure the entire teeth campaign exists to name, one level up. A green
    suite is not evidence of a defended contract; a clean sweep is not evidence of a clean
    corpus. Both are absence-of-findings read as absence-of-defects.

  THE CHEAP DISCIPLINE
    Before believing a sweep, ask what it did NOT probe, and check that number against the
    corpus by hand. `grep -c` on the pattern the tool matches, compared to the number of
    rows it printed, would have caught all three in seconds. That is the sweep equivalent
    of the before-table: not "did it find anything" but "did it look everywhere it claims".
