3. THE HAZARD, MEASURED — and the amendment it falsified
----------------------------------------------------------------------------------------------
    position on its process       draws   died  no-file  rate
    1st draw (fresh restart)         17      7        0    41%
    draw 2 (RESTART=0)                8      5        0    62%
    draw 3 (RESTART=0)                2      1        0    50%
    draw 4 (RESTART=0)                1      0        1   100%

    FIRST draws 7 of 17 lost (41%)   ·   LATER draws 6 of 11 lost (55%)

Cause, from the server logs: `libc++abi: terminating due to uncaught exception of type
std::runtime_error: [METAL] Command buffer execution failed: Impacting Interactivity`. The macOS
GPU watchdog is killing long compute command buffers under contention. It is not the model, not
the spec, and not the protocol — and it is invisible to every check this campaign owns except the
one that noticed the process was gone.

📌 **AMENDMENT 3 SAID THE OPPOSITE AND IT WAS MINE.** Off eleven rows counted by eye I wrote that
the deaths were position-independent and that "the prompt-cache-growth story I would have guessed
is not what the ledger says". Four rows later it was 25% against 57%. The amendment is left in
place with the correction under it. NINTH hand-counted number this campaign has had to fix, and
the first one caught the same night, before any result log quoted it — which is only true because
the fix was to build `_draw_hazard.py` rather than to recount.

⚠️ WHAT THE HAZARD NUMBER DOES NOT SAY: position and spec are confounded by the design. Every arm
after the first is RESTART=0, and on this hunt every second draw was the same +54 screen spec —
the longest prompt in the set. n=11 cannot separate "later draws die" from "that spec dies". The
tool prints both tables side by side for that reason.
