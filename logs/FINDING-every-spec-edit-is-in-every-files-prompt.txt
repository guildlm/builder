FINDING — every spec edit is in EVERY file's generation prompt, by construction
==============================================================================
30 July, 12:30. Found by asking a structural question about the pipeline instead of inferring it
from a diff, while the ledger prose arm was at 3 of 19 and ungraded.

WHAT THE CODE SAYS
src/builder.py:1076, inside the per-file GENERATION prompt:

    f"TARGET_FILE: {task.spec.path}\n"
    f"Purpose of this file: {task.spec.purpose}\n\n"
    f"All files in this project:\n{_file_list(spec)}\n"

and src/builder.py:1265:

    def _file_list(spec: Spec) -> str:
        return "\n".join(f"  - {f.path}: {f.purpose}" for f in spec.files) + "\n\n"

_file_list renders EVERY file's path AND ITS FULL PURPOSE TEXT. So when generating file 17, the
model is shown file 2's purpose verbatim. A one-line edit anywhere in the spec is present in all
nineteen prompts, not just in the prompt for the file it belongs to.

WHY THIS MATTERS FAR BEYOND THIS ARM — IT DEFLATES THE WORD "PROPAGATED"
The nine-arm collateral series has been reporting results in the shape "the edit propagated to a
file it does not mention", and the 19->19 taskflow arm's PROSE ECHO was written up as the model
"following a rename across a file boundary". That language implies inference or leakage.

    There is nothing to infer. The renamed identifier was sitting in that file's own prompt, in
    the plan block, as part of another entry's purpose text. The model did not carry the change
    across a boundary — the change was already on its side of the boundary.

    So "collateral" in this series measures: given that the changed text is in the prompt for
    every file, how often does the OUTPUT of an unrelated file change too? That is a real and
    interesting question. It is a much smaller and less mysterious one than the write-ups implied,
    and every one of those write-ups is mine.

WHAT IT EXPLAINS, AND WHAT IT STILL DOES NOT
    EXPLAINS why the non-rename column is 6 of 6. The edited text is in nineteen prompts; a spec
             edit is nineteen prompt edits. Perturbation everywhere is the DEFAULT expectation,

    EXPLAINS the prose echo without any cross-file inference.
    DOES NOT explain the NULLS, and they are now the interesting column. Five arms changed the

    ⚠️ THE SERIES' QUESTION WAS BACKWARDS. "Why did this edit spread?" has a boring answer: it was

THE TWO GAPS, NOW CLOSED (12:34) — and one of them kills a candidate explanation
    1. FIX PROMPTS DO NOT CARRY IT. `_file_list` is called in exactly ONE place in the whole file:
       line 1076, the generation prompt. The fix prompt at 5797 builds TARGET_FILE and Purpose
       without it. So the edited text is in all 19 GENERATION prompts and in NO fix prompt.
       Moot for every arm in this series — as-drawn grading reads .pre-fix.json, which is the tree
       before any fix round runs — but it means fix-round behaviour cannot be attributed to the
       edit's text at all, and any future arm graded post-repair would need that stated.

    2. NO TRUNCATION. Nothing anywhere trims purpose text: every "truncat" in builder.py is about
       a truncated MODEL RESPONSE or a truncated import path, not the plan block. Purposes render
       in full regardless of spec length.

       ⚠️ THAT KILLS THE MOST ATTRACTIVE EXPLANATION FOR THE NULLS. "The edit was too far from the
       file to reach its prompt" would have explained why five arms changed nothing — a cheap,
       mechanical answer. It is false. The edit reaches every generation prompt, in full, always.
       ledger's edit sat in nineteen prompts and eighteen files came out byte-identical.

       So the nulls are not a reach problem. They are the real phenomenon, and the series has no
       mechanism for them.

    3. RETRIEVAL, CHECKED AT 12:38 — AND IT CORRECTS WHAT I WROTE HERE MINUTES EARLIER.
       I wrote: "For money.go itself [the selector] changes, which is one more reason its identical
       output is notable." The selector TEXT changes; the SHOTS DO NOT. Retriever.top_k (line 417)
       scores Jaccard over `set(re.findall(r"[a-z0-9]+", query.lower()))` — a token SET, so it is
       completely order-insensitive. A transposition of two comma-separated words leaves the set
       identical, hence identical scores, hence identical shots.

       So money.go's prompt differed ONLY in the two transposed words, in its own purpose and in
       the plan block. Its byte-identical output is LESS surprising than I claimed, not more.

    AND THE TWO ARM KINDS DIFFER HERE, WHICH NOBODY NOTICED — measured, not argued:
       PROSE transposition ("strconv, strings" -> "strings, strconv")
           selector text differs: YES · retrieval token SET differs: NO
       NAME transposition (TestBalanceMissingAccount -> TestBalanceAccountMissing)
           selector text differs: YES · retrieval token SET differs: YES
           symmetric difference: {testbalancemissingaccount, testbalanceaccountmissing}
       An identifier is ONE token to `[a-z0-9]+`, so reordering words INSIDE it swaps one token for
       another. Reordering words in prose does not change the set at all.

       ⚠️ AND THE OUTCOMES RUN THE WRONG WAY. taskflow's prose swap ("(sync, sort, errors as
       needed)" -> "(sort, sync, ...)") also leaves the token set identical — so its prompt differed
       in two transposed words and nothing else — and it PERTURBED 6 CODE files and 8 functions.
       The ledger NAME swap changed a retrieval token AND its plan-block text, and changed 0 files.

           smaller prompt perturbation, identical retrieval  -> 6 files changed
           larger prompt perturbation, retrieval token moved -> 0 files changed

       Whatever separates perturbing arms from null ones, it is not the size of the prompt
       difference, and it is not whether retrieval moved. Both point the opposite way.
