WHAT THE FOUR CODE DIFFERENCES ACTUALLY ARE (20:09) — an API change, propagated
================================================================================
Read the largest of them, store.go at 2881 vs 2404 bytes. It is not noise and not formatting:

    control  type StoreImpl struct { ... }   func NewStore() *StoreImpl
    dose     type store     struct { ... }   func NewStore() *store

THE DOSE DRAW UNEXPORTED A PUBLIC TYPE. `StoreImpl` — exported, part of the package's API
surface — became `store`, unexported. Every method receiver went with it, and so did the two
other CODE files:

    projects_handler.go   control mentions StoreImpl 2x · dose 0x
    tasks_handler.go      control mentions StoreImpl 2x · dose 0x

So three of the four CODE differences are ONE decision propagating. The fourth, middleware.go,
is a separate change at identical byte length.

    exported declarations in store.go   control 3 · dose 2

The dose draw also added a compile-time interface assertion the control does not have:

    var _ Store = (*store)(nil)

    A GOOD line, incidentally — it pins the impl to the interface at compile time. The point
    is not that either version is worse. It is that TWELVE LINES OF PROSE ABOUT NAMING A
    VARIABLE `t` IN A TEST changed a package's exported API and added an assertion in an
    implementation file, in a spec entry that mentions none of it.

⚠️ AND IT SHARPENS WHAT "CODE DIFFERENCE" MEANT IN THE TASKAPIPRO ARM TOO. There the three
were an entire `getenv` helper present in one arm and absent in the other, a statement body in
service.go, and models_test.go. Both specs show the same character: not a token here or there,
but whole declarations appearing, disappearing, or changing visibility.

⚠️ WHAT IT DOES NOT SHOW. Which version the spec asked for. The taskflow spec's store entry

ANSWERED 20:13 — THE SPEC ASKED FOR NEITHER, AND ALL THREE DRAWS DEVIATE
=========================================================================
The section above left open "which version the spec asked for". Read it:

    specs/taskflow.yaml, store.go entry:
      "A Store STRUCT holding two maps (tasks map[string]Task, projects map[string]Project)
       guarded by a single sync.RWMutex, built by NewStore()."

    what the draws built:
      taskflow-chain4   type Store INTERFACE + type StoreImpl struct + NewStore() *StoreImpl
      taskflow-chain5   type Store INTERFACE + type StoreImpl struct + NewStore() *StoreImpl
      taskflow-dose     type Store INTERFACE + type store     struct + NewStore() *store

    NONE of them produced a `Store` struct. All three invented an INTERFACE named Store and
    put the maps in a second type the spec never mentions. The three draws agree on the
    deviation and disagree only on what to call the invented type.

    SO IT IS NOT "WHICH ONE IS RIGHT". Both are wrong, in the same way, and the twelve lines
    moved the draw between two flavours of a deviation the spec did not ask for.

⚠️ AND THAT MAKES THE DIFFERENCE SHARPER, NOT SOFTER. A spec-compliant draw has one obvious
target to hit; an unconstrained invention has many, and the twelve lines are enough to move
which one gets picked. The perturbation is landing precisely where the spec left room.

    That is a testable follow-on and it is NOT run: tighten the store entry to name the struct
    explicitly, redraw both arms, and see whether the perturbation survives being pinned. If
    it does, dose beats specificity; if it does not, the practical mitigation for the whole
    finding is "say exactly what you want" rather than "keep entries short".

⚠️ IT ALSO MEANS THE CAMPAIGN'S OWN INSTRUMENTS NEVER FLAGGED THIS. Every taskflow draw for
weeks has invented an interface where the spec asked for a struct, and every one converged
GREEN — because a green suite tests behaviour, not shape, and the spec audits check test names
and promised guards. It is the same blind spot _stub_files.py found in the store split, on the
same file, in a different spec.
